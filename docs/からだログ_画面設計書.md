## 1. 全体構成(ナビゲーション)

ボトムナビゲーション3タブ構成とする。

| タブ | 役割 |
|---|---|
| ホーム | 起動時に表示。その日の体重・食事・水分・日記・筋トレの記録をまとめて表示 |
| 推移 | 体重・カロリー・水分のグラフ、目標までの進捗確認、週次レビュー(8.2章)・月次レビュー(8.3章) |
| 設定 | 目標体重/目標日の設定、身体プロフィール、目標カロリー・PFC目標・目標水分摂取量、データ同期、食事マスタ・種目マスタ・習慣マスタ管理 |

記録の入力は、ホーム画面の各カード・ラベルを直接タップして対応する記録画面に遷移する形で行う(2章参照)。**フローティングアクションボタン+アクションシートによる「体重を記録」「食事を記録」の選択導線は、この直接タップ導線と役割が重複するためMUI移行(Issue #27)時に廃止した**(12章「決定済みの論点」参照)。

## 2. ホーム画面

### 表示する日付(Issue #226)

- ホームは既定で**当日**を表示するが、**日付ナビ(◀ / ▶)で過去日に切り替えられる**。表示日は `?date=YYYY-MM-DD` で持ち、リロード・共有しても同じ日が開く。未来日・不正な値は当日に倒す(未来の記録は存在しないため)
- 過去日を表示中は、見出しを「昨日の記録」「一昨日の記録」「◯日前の記録」に変え、**1タップで当日へ戻る「今日へ」ボタン**を出す(◀▶の連打で戻らせない)。当日は従来どおり時間帯に応じた挨拶文
- 各カードの見出しの「今日の〜」は過去日では「この日の〜」に変わる(摂取カロリー・食事・習慣・血圧の測定値)
- **記録の追加・編集は過去日でもできる。** 各カードの遷移先に表示日を引き継ぎ、日付キーの記録画面(体重・血圧・周囲径)には過去日のとき `create=1` を添える — ホームからの遷移は「明示的な追加の意思」とみなす(#141で履歴から過去日を追加できるようにしたのと同じ扱い)
- **連続記録日数は「その日時点」の値を出す。** 当日だけ「未記録でも前日までの連続を継続中と数える」猶予を認め、過去日はその日が未記録なら0とする(`streakDaysEndingOn`)。過去日ではチップの文言も「連続◯日」(「記録中」を付けない)

### 表示内容
- 表示中の日付
- 連続記録日数(フェーズ3、Issue #46)
  - 「記録した日」(その日に食事記録が1件以上、または体重記録がある日)が何日連続しているかを表示する。当日まだ未記録でも、前日まで連続していれば「継続中」として表示する(当日の未記録で即座に途切れた扱いにしない)
  - 常時表示のUIのため **accent色は使わない**(デザインガイドの制約。accentは達成の瞬間の演出専用)。日数の節目での達成演出を入れる場合のみaccentを使ってよい
- 体重・体脂肪率(当日1件のみ表示。同日に複数回記録した場合は最後に保存した値で上書きされる=後勝ち。体脂肪率は未記録なら非表示)
  - 体脂肪率も体重と同様、前回記録との差分(前回比 ±◯.◯%)をカード内に表示する。比較対象となる前回記録に体脂肪率が無い場合(前回未計測など)は「体組成計より」を表示する
  - 体重・体脂肪率カードはタップすると体重記録画面へ遷移する。当日分の記録が既にあればその値を編集、なければ新規入力になる(3章参照)
- 食事記録一覧(朝食/昼食/夕食/間食の4区分。1区分=1つの入り口カード。未記録の区分は破線カードで「未記録」と表示)
  - 記録済みの区分カードには、品目数(「◯品」)・料理名のプレビュー(全品目名を「、」でつないだ1行。溢れは省略)・区分の合計カロリーを表示する。区分内に未同期の品目があれば「未同期」チップを出す。「食べなかった」として記録した区分は「◯品」の代わりに落ち着いた配色の「食べなかった」バッジのみを出し、料理名プレビュー・kcalは表示しない(未記録の破線カードとは見た目で区別する。4章「食べなかった」の記録・Issue #143)
  - 区分カードは行全体が1つのタップ領域。タップするとその区分の記録画面が開き、その区分の当日分の全品目をまとめて編集できる(記録済み・未記録どちらも同じ導線。単品ごとの編集導線は廃止。4章参照。Issue #126)
- 当日の摂取カロリー合計、目標カロリーとの差分(「あと◯◯kcal食べられます」、目標超過時は「◯◯kcalオーバーしています」の形で表示)
- 当日の摂取PFC合計(たんぱく質/脂質/炭水化物、それぞれグラム表示)
  - PFC目標値(9章参照)が設定されている場合は「実績g / 目標g」の対比表示にする。未設定の場合は従来どおり実績のみ(フェーズ3、Issue #47)
- その他の記録セクション(食事セクションの下に「水分」「日記」「筋トレ」「血圧」「周囲径」の行を表示。血圧・周囲径はフェーズ4、Issue #117・#118)
- 水分行
  - 当日合計ml(目標摂取量が設定済みの場合は「合計 / 目標ml」+進捗バー、未設定の場合は合計mlのみ)を表示する
  - タップすると水分記録画面へ遷移する。クイック追加・記録内訳の確認・削除はすべて記録画面側で行う(5章参照)
- 日記行(水分行の下)
  - 当日分の本文があれば冒頭を数十文字程度でプレビュー表示し、気分タグを設定していればラベルチップで併記する。未記録なら「未記録」と表示する
  - タップすると日記入力画面へ遷移する。当日分の記録が既にあればその内容を編集、なければ新規入力になる(6章参照)
- 筋トレ行(日記行の下)
  - 当日分の記録があれば「◯種目・◯セット」のサマリーを表示し、無ければ「未記録」と表示する
  - タップすると筋トレ記録画面へ遷移する。当日分の記録があればその内容がドラフトとして読み込まれ、追記・修正・削除がすべて記録画面側で行える(7章参照)
- 血圧行(フェーズ4、Issue #117)
  - 当日の測定値があれば「最高/最低 mmHg」を表示し、無ければ「未記録」と表示する。タップすると血圧記録画面へ遷移する(当日分があれば編集、なければ新規)
- サイズ(周囲径)行(フェーズ4、Issue #118)。**画面の表示ラベルは「サイズ(おなか周り)」**とし、測定用語の「周囲径」は避けて柔らかくする(記録画面のタイトルも「サイズを記録」、主フィールドの腹囲は「おなか周り」表記。内部の型名 `BodyMeasurementRecord`・同期シートのタブ名「周囲径記録」は変えない)
  - 最新のおなか周り(cm)と測定日を表示し、記録が無ければ「未記録」と表示する(月1程度の低頻度入力のため当日でなくても最新値を出す)。タップすると記録画面へ遷移する
- 今日の習慣セクション(その他の記録の下。フェーズ4、Issue #113)
  - アクティブな習慣をチェックリスト形式で表示し、タップで当日のチェックをON/OFFする。習慣ごとに連続日数・直近7日の達成状況を併記する(#46の仕組みを流用)。アクティブな習慣が無ければセクションごと非表示(管理は設定画面の習慣マスタ)
- SNS共有カード(Issue #235。習慣セクションの下)
  - 当日の記録を1枚のカード画像にして保存・共有できる導線。当日に載せられる数字が1つも無ければセクションごと非表示。詳細は2.1章
- 各記録の同期状態(スプレッドシートへ未同期の場合は「未同期」のラベルを控えめに表示。10章の同期フロー参照)

### 2.1 SNS共有カード(Issue #235)

※実装状況: 実装済み(Issue #235。2026-08-19)。導線は `src/components/ShareCardLauncher.tsx`、載せる数字の決定は `src/lib/shareCard.ts`(純関数)、描画は `src/lib/shareCardCanvas.ts`。

- ホームと週次レビュー(8.2章)から、記録のサマリーを**カード画像(PNG)として書き出す**。要件は要件定義書4.9章
- **日次カードはホームの表示日に追従する**(Issue #226)。過去日を表示していればその日のカードになり、見出し・キャプションも「今日の〜」ではなく「この日の〜」になる。前日分のカードを翌朝に作れるのはこのため
- 「画像をつくる」でボトムシートが開き、プレビュー・「体重の数値を隠す」トグル・「画像を保存」「共有」が並ぶ。共有ボタンはWeb Share APIがある端末でのみ表示する(PCでは保存のみ)
- **載せる数字の決定は純関数に閉じ、描画はその結果を置くだけにする** — 週次レビューが `WeeklyDigest` の値をそのまま表示するのと同じ方針で、数字を決める場所を1か所にするため
  - 主数値は値のあるものを優先順に1つ選ぶ(週次=週平均体重 → 前週比 → 平均摂取 → 記録した日数、日次=体重 → 前回比 → 摂取カロリー)。体重を主数値にした場合のみ、右に前週比・前回比のバッジを置く(減=teal / 増=coral)
  - 並べる数値は最大4項目。値の無い項目は詰めて表示する(空欄を出さない)
  - **日次のみ、筋トレの内訳を主数値の横に明細として置く**(「ベンチプレス 60kg×8回 3セット」の形。見出しに「◯種目・◯セット」を併記)。種目の区切りは名前ではなく `exerciseOrder`(同じ種目名を別カードとして2回記録できるため。履歴確認画面の数え方に揃える)。重量・回数はセットごとに違えば範囲で示し(「50〜60kg×6〜10回」)、重量0は「自重」と表記する。行数の上限を超える日は残りを「ほか◯種目」にまとめる。明細を出す日は、バッジ(前回比)が明細の列に重ならないよう主数値の横ではなく見出し行に置く
- **体重の数値を隠すトグル**: 体重の実数を伏せ、増減だけを残す。伏せている間は「目標までの残り」も出さない(公言している目標体重との差から実数が復元できるため)。体重の記録がある期間でのみトグルを出す
- 画像は1200×675(16:9)を2倍解像度で書き出す。クリームの地に白いカードを置き、**見出し行の右端に署名(アプリアイコン + アプリ名)を置く**(フッターは持たない)。**アイコンはPWAアイコンのマスターのコピー(`public/icons/icon.svg`)を読み込んで描く**(canvasに描き写すとマスターと乖離するため)。**URLは載せない**(投稿本文側にリンクを置くため)。**accent(黄)は使わない**(達成の瞬間専用。デザインガイド)。**絵文字も使わない**
- 縦の配置は`shareCardCanvas.ts`の先頭にY座標の定数としてまとめてある。フッターが無い分の余白は各段に配ってあり、**明細の最終行(4行目または「ほか◯種目」)と数値欄のラベルが重ならないこと**が動かすときの制約
- 画像はcanvas 2Dで手描きする(グラフを手書きSVGにしているのと同じく、パレットを厳密に制御するため。外部ライブラリを足さない)

## 3. 体重記録フロー

1. ホーム画面の体重・体脂肪率カードをタップする(当日分の記録が既にあればその値を編集、なければ新規入力)
2. 体重入力画面が開く
   - 日時: 現在時刻がデフォルト(タップで変更可能)
   - 体重: 数値入力欄で入力(スマホでは数値キーボードが開く)。入力すると前回記録との差分(前回比 ±◯.◯kg)を入力欄の下に小さく表示する
   - 体脂肪率(任意): 体重と同様の数値入力欄。体組成計での計測値がない日は未入力のままでよい
   - メモ(任意): 「筋トレ後」「飲み会翌日」など一言メモ欄
3. 保存ボタンで確定 → ホーム画面に戻り、当日の一覧に反映される

- 1日1件のみ記録する仕様とする。同日に2回目以降を保存した場合は、その日の記録を新しい値で上書きする(後勝ち)

## 4. 食事記録フロー

食事記録は**区分(朝食/昼食/夕食/間食)を入り口にした「1区分1画面」方式**を採る(筋トレ記録と同じ構造。Issue #126)。ホーム・履歴の各区分カードから、その日のその区分の記録画面を開き、画面内で品目を複数登録して**その区分の当日分をまとめて置き換え保存**する。新規/編集で画面を分けず、既存の記録は下書きとして読み込む(筋トレの `StrengthRecordPage` と同じ考え方。12章にあった「1画面にまとめるか2画面に分けるか」の論点は、区分単位1画面で決定済み)。

1. ホーム画面の区分カード(未記録・記録済みとも行全体)、または履歴の区分行をタップして食事記録画面を開く。URLは `/record/meal?type=<区分>&date=<日付>`(`date` 省略時は当日)。区分は入り口で確定するため、画面内に区分の切り替えUIは持たない(URLの区分が不正・未指定のときのみ、現在時刻から一番近い区分をフォールバックで選ぶ)
2. 画面の構成(上から):
   - **日時**: その区分の全品目で共有する1つの日時。当日新規は現在時刻、過去日新規はその日の12:00、既存の記録があるときは先頭品目の日時を初期値にする(変更可)
   - **写真から記録する**: 補足情報(任意のテキスト。例: 「唐揚げ弁当、ご飯少なめ」)を添えて、撮影またはライブラリから写真を選択 → AIが写っている料理・食品を品目ごとに個別に判定する(Issue #50)。写真は最大4枚まで添付でき(ライブラリは複数選択可、撮影は1枚ずつ追加。サムネイル一覧から1枚ずつ取り消し可能)、複数枚はすべて「同じ1回の食事」の写真として1回の解析にまとめて送られる(Issue #110)。**解析結果は検出された品目ぶんの品目カードとして下部リストに追加される**(1品でも複数品でも同様)。反映後は件数を通知し、各カードで内容を確認・修正できる。自動で保存はされず、確認・修正は品目カード上で行うため、旧方式の「検出リストからタップで1品ずつフォームに反映」や「未追加のまま保存する際の確認ダイアログ」は不要になった。量や内容の判定の自信が低い場合は、その旨の注意文言を表示する
   - **よく食べるものから選ぶ**: 食事マスタを品目名で検索でき、一覧はページネーション(6件/ページ)で表示する。選ぶと登録済みの固定値が入った品目カードが追加される
   - **品目カードのリスト**: 1品=1カード。料理名・カロリー・PFC(たんぱく質/脂質/炭水化物)をインライン編集し、カードごとに削除・「この品目をマスタに登録」ができる。「品目を追加」ボタンで空のカードを足せる。写真判定・マスタ選択・手入力のどれで足した品目も、保存前にこのカード上で必ず確認・修正できる
   - **区分の合計**: 品目カードの合計カロリー・PFCを画面下部に表示する
3. 保存ボタンで、その区分の当日分を丸ごと置き換えて確定する(下記の「置き換え保存」参照)。当日はホーム、過去日は履歴(食事)に戻る

### 「食べなかった」の記録(Issue #143)

日時フィールドの下に「この◯食は食べなかった」トグルを置く。ONにすると写真AI・マスタ選択・品目カードなど品目入力のUIを丸ごと隠し、代わりに「品目の入力は不要」という案内カードを出す。保存ボタンのラベルも「食べなかったと記録する」に変わる。

- データ上は通常の品目入力と同じ「区分単位の丸ごと置き換え」(下記)に乗せる。`confirmedName: "食べなかった"`・kcal/PFCすべて0・`skipped: true` の `MealRecord` を1件だけ保存する
- **「未記録」(その日・その区分にMealRecordが0件)と「食べなかった」(skipped:trueの1件がある)は明確に区別する。** 記録率(8.2章・Issue #46)は「食事1件以上または体重記録あり」で日を数えており、「食べなかった」もMealRecordの1件としてこれに乗るため、記録率の計算に追加対応は不要(食べなかったことを記録する、という行為自体を「その日記録した」とみなす)
- ホーム(2章)・履歴(8.1章)の区分行では、通常の「◯品」バッジの代わりに落ち着いた配色の「食べなかった」バッジを出し、料理名プレビュー・kcal数値は表示しない(0kcalの品目として紛れないようにするため)
- 既存の記録を1件だけ・`skipped:true` で持つ区分を開くと、自動でこのトグルがON状態で読み込まれる(通常の下書き読み込みと同じ考え方)。OFFに戻すと通常の品目入力(空カード1枚)に戻る
- 同期用スプレッドシートの食事記録タブに `skipped` 用の列は追加していない。「食べなかった」の記録は品目名「食べなかった」・kcal=0の行としてシートに書き出され人が見て意味は分かるが、シートからの再取り込み時は通常の0kcal品目として復元され、`skipped` の特別表示は復元されない(AI推定値・写真参照が取り込みで復元されないのと同じ制約。10.1章参照)

- 完全に空の品目カードは保存時に除外される。料理名が空で数値だけ入ったカードは何の記録か分からないため保存をブロックする(筋トレでセットだけ入力された種目をブロックするのと同じ考え方)
- 写真はAI判定への送信時に1枚ずつ長辺1024pxへリサイズ・JPEG圧縮され、判定にのみ使われる。**現時点では写真自体を端末に保存しない**(保存するかどうかは12章の論点)

### 置き換え保存(Issue #126)

保存は、その区分・その日の既存レコードをすべて削除してから、画面上の品目を新規レコードとして登録し直す「丸ごと置き換え」方式(筋トレの当日置き換えと同じ。`replaceMealRecordsForDateAndType`)。

- 品目を空にして保存すれば、その区分の当日分の削除になる
- 置き換えのたびに各品目へ新しいIDを振り直すため、置き換え前の全レコードIDを削除トゥームストーンとして残し、スプレッドシート側の古い行を次回同期で消す(Issue #30の削除反映を流用)。新規レコードは `synced: false` で登録され、次回同期の対象になる
- 区分内の全品目は同一の日時を共有するが、品目の並び順を保つため各品目の `timestamp` に品目インデックスぶんのミリ秒を加算する(同一分内の差で表示・集計には影響しない)
- 置き換えの対象は「その日・その区分」に限定され、同じ日の別区分や別の日の同区分には影響しない
- 単品ごとの編集画面(旧 `?id=<MealRecord.id>`)・区分セグメント・「もう1品追加」ボタン・追加専用の入力欄(旧 `ManualMealItemAdder`)は、この方式への移行で廃止した

### 4.1 食事マスタ管理

- 食事マスタ(登録済みの「よく食べるもの」)の一覧・編集・削除は、設定画面から遷移する専用画面(食事マスタ管理画面)で行う(9章参照)
- 一覧の各項目は名前・カロリー・PFCを表示し、その場でインライン編集または削除ができる
- 品目名での検索・ページネーションを備える
- 一括登録は同期用スプレッドシートの「食事マスタ」タブへ行を直接書き込み、「シートから取り込み」(10.1章参照)を実行する運用とする(Issue #96)。かつてコードに埋め込んでいた定番メニューのシードデータ(外食チェーン・コンビニの定番。「定番メニューを一括登録」ボタンで投入)は、シート貼り付け用のサンプル `docs/data/食事マスタ_定番メニューサンプル.csv` へ退避して撤去した
- 手動での新規追加(名前・カロリー・PFCを直接入力して1件登録)ボタン(一覧下部の破線ボーダーのボタン。Issue #35)
- 重複登録(似た名前・同じ商品が複数件になる)の自動マージは行わず、気づいたユーザーが手動で整理する想定とする

## 5. 水分記録フロー

ホーム画面の水分行をタップして専用の記録画面(水分を記録)へ遷移し、クイックタップで当日の摂取量を積み上げる構成とする(2章参照)。フェーズ2で詳細を決定(Issue #9。当初はホーム画面内でのワンタップ完結+手入力モーダルの構成としていたが、デザインプロトタイプの確認により専用画面+4ボタン構成に変更。意思決定ログ参照)。

1. ホーム画面の水分セクション(2章参照)をタップすると水分記録画面が開く
2. 画面上部に当日の合計カード(当日合計ml / 目標ml + 進捗バー)を表示する
   - 目標摂取量(9章参照)が未設定の間は進捗バーを表示せず、「設定画面で目標を設定すると、達成度を表示できます」の案内文を表示する
3. クイック追加ボタン(200 / 300 / 500 / 2000ml の4ボタン。当初は100/200/350/500mlで500mlをプライマリ強調としていたが、Issue #79で実際の飲用シーンに合わせて量を変更し、強調は廃止して全ボタン白抜きに統一)をタップすると、タップした瞬間の時刻・その量で記録が1件追加される(確認ダイアログなし。誤タップした場合は後述の記録リストから削除する)
   - 任意量の手入力は設けない(端数はボタンの組み合わせで近似する。ボタン量のカスタマイズ可否と合わせて12章の論点)
4. 合計カードの下に「今日の記録」リスト(時刻・量、新しい記録が上)を表示し、各行に削除ボタンを設ける。誤って記録した場合は削除し、必要なら正しい量で記録し直す(量そのものを編集するUIは持たない。クイック記録主体のため、削除→再記録の方が手間が少ないと判断)
   - 記録が0件の場合は空状態文言(「まだ記録がありません」)を表示する

- 1日の目標摂取量は設定画面(9章参照)で設定する(ml、手動入力、初期値未設定)。設定済みの場合のみホーム行・記録画面に進捗バーを表示する
- 推移画面(8章参照)に日別摂取量の推移グラフを追加する。カロリー推移グラフと同様、記録の無い日も0mlで埋めて欠損を隙間として表示し、目標ラインがあれば重ねて表示する
- 水分関連のUIはコーラル系ではなくブルー系(#3AA0DB / #2B7BB0 など)の配色を使う(水を想起させるため。デザインプロトタイプ参照)
- 履歴確認画面(8.1章)への統合は実装済み(#73。日付ごとに集約した1日1行で表示)
- スプレッドシート同期の対象に含める(#72で決定・実装済み。10章参照)。体重・食事と同様の削除トゥームストーンの仕組みを流用する
- クイック追加ボタンの量(200/300/500/2000ml)を設定でカスタマイズ可能にするかは今後検討(12章参照)。現状は固定値とする

## 6. 日記フロー

体重と同様、日付をキーとした1日1件の記録とし、ホーム画面からの直接タップで記録画面に遷移する構成とする(2章参照)。フェーズ2で詳細を決定(Issue #10)。

1. ホーム画面の日記セクションをタップする(当日分の記録が既にあればその内容を編集、なければ新規入力)
2. 日記入力画面が開く
   - 日付: 当日固定(体重と同様、日付が記録のキーになるため過去日の新規作成はこの画面からは行わない)
   - 気分タグ(任意): 「絶好調 / 良い / 普通 / 眠い / 不調」の5段階から1つ選択できるタイル(手描きストローク調の表情アイコン+ラベル。選択中はアンバー枠。当初は3段階の想定だったが、デザインプロトタイプの確認により5段階に変更。意思決定ログ参照)。テンプレート項目(体調・睡眠時間など)は持たない
   - 飲酒タグ(任意): 「飲酒あり」のトグル1つ(#112)。気分タグと同列の任意入力で、週次レビューのクロス分析(8.2章)の集計軸に使う。ONで保存した日だけ`alcohol: true`を持ち、OFFは「飲酒なし」ではなく「記録なし」(undefined)として扱う。飲酒は食事記録にカロリーとして載っていても「飲んだ日」というフラグにはならないため、1日単位の事実として日記側に持たせる(意思決定ログ参照)
   - 本文: 自由記述のテキストエリア(任意。「ひとこと日記」)
3. 下部固定の保存ボタンで確定 → ホーム画面に戻り、当日のプレビューに反映される

- 1日1件のみ記録する仕様とする。同日に2回目以降を保存した場合は、その日の記録を新しい内容で上書きする(後勝ち。体重記録と同じ考え方)
- 本文・気分タグ・飲酒タグのすべてが空の状態で保存した場合は、その日の記録を削除する(未記録に戻す)。この挙動により明示的な削除ボタンは設けない
- 写真添付はMVPでは行わない(テキストと気分タグのみ)
- 更新すると同期状態は`synced: false`にリセットされ、次回の同期対象になる(#72で同期対象に追加済み。10章参照)
- 履歴確認画面(8.1章)への統合・過去分の編集導線は実装済み(#73。履歴の日記行タップで`?date=YYYY-MM-DD`付きの日記入力画面を開き、過去日を編集できる)

## 7. 筋トレ記録フロー

ホーム画面の筋トレ行をタップして記録画面(筋トレを記録)へ遷移し、当日の全種目・全セットを1画面でまとめて編集する構成とする(2章参照)。フェーズ2で詳細を決定(Issue #8。当初は「1画面1種目+セット逐次確定」の構成としていたが、デザインプロトタイプの確認により「1画面で当日の複数種目をまとめて編集」に変更。意思決定ログ参照)。

1. ホーム画面の筋トレセクション(2章参照)をタップすると筋トレ記録画面が開く
   - 当日分の記録が既にあればその内容がドラフトとして読み込まれ、追記・修正・削除がすべてこの画面で行える(新規/編集で画面を分けない)
   - 当日分が無ければ、空の種目カード1枚(名前空欄+空セット1行)の状態で開く
2. 種目カードを縦に並べて編集する。各カードの構成:
   - 種目番号バッジ+種目名入力欄(自由入力。種目マスタ(7.1章参照)に登録済みの種目名は入力候補としてサジェスト表示される)+種目削除ボタン
   - 種目名が過去の記録にある種目と一致した場合、種目名欄の下に「前回 M/D + 前回の重量×回数」の参照行を表示し、「入力」ボタンでその内容をセット欄へ一括転記できる(Issue #100。下記の入力補助の項参照)
   - セット行のリスト(セット番号+重量(kg)・回数の数値入力欄+行削除ボタン)
   - 「セットを追加」ボタン(破線)で空のセット行を追加する
3. 末尾の「種目を追加」ボタン(破線)で種目カードを追加する
4. 下部固定の保存ボタンで当日分をまとめて確定する → ホーム画面に戻り、当日のサマリーに反映される
   - 保存時、重量・回数がどちらも空のセット行と、名前もセットも空の種目カードは除外する
   - 保存は「当日分の置き換え」として動作する(既存の当日レコードを消して保存内容で登録し直す)。すべての種目を削除して保存すれば当日分の削除になるため、明示的な削除ボタンは設けない

- 記録粒度はセット単位(1セット=1レコード。種目名・セット番号・重量kg・回数を持つ。11章参照)。記録日時は保存時刻を全レコード共通で持つ
- 種目マスタは種目名のみを持ち、重量・回数はマスタ化しない(毎回変わる値のため)
- 前回記録値は「自動prefill」ではなく「参照表示+任意の転記」として持つ(Issue #100): 種目名が過去の記録と一致すると、その種目を最後に記録した日の重量×回数を参照表示し、ユーザーが「入力」ボタンを押したときだけセット欄へ転記する。開いた瞬間に勝手に埋めないことで記録画面をシンプルに保ちつつ、繰り返し種目の再入力の手間を減らす。比較対象は編集中の日より前の最新記録(当日は含めない)
- メモ欄・保存時のマスタ自動登録は持たない(記録画面をシンプルに保つ。要否は12章の論点として再検討)
- 保存すると当日分の各セットレコードは`synced: false`で登録し直され、次回の同期対象になる(#72で同期対象に追加済み。置き換え保存に伴うID振り直し・削除トゥームストーンの扱いは10章参照)
- 推移画面でのグラフ表示(重量推移など)はMVPでは行わない。まずは記録の蓄積とホーム画面での一覧確認を優先し、グラフ化の要否は12章の論点とする
- 履歴確認画面(8.1章)への統合は実装済み(#73)。推移グラフへの統合は引き続き12章の論点

## 8. 推移画面

- **グラフ共通の見やすさ方針(Issue #128)**: 各グラフは「今どうなっているか」を一目で読めるよう、以下を共通で備える。パレット・手書きSVGの方針(CLAUDE.md参照)は据え置き、アクセントの黄色は使わない。
  - **カード見出しに数値を出す**: 現在値+期間内の変化量チップ(体重・体脂肪率・おなか周り)、期間平均(カロリー・水分・歩数・睡眠。未記録日=0は除いた平均)、最新値(血圧は最高/最低)。変化量は矢印アイコンを使わず符号(−/+)と色で示し、体重・体脂肪率・おなか周りは「減る=前進」のためティール、増加を注意色(赤)にする
  - **最新を強調**: 折れ線は最新の点を大きくリング付きで、棒グラフは最新(=末尾。通常は今日)の棒を濃色+値ラベルにして「今」を目立たせる。棒グラフのX軸末尾ラベルは「今日」を強調色で表示する
  - **面塗り**: 折れ線(体重・体脂肪率・おなか周り)の下にセカンダリ色のグラデ面塗りを重ねる。血圧は最高〜最低の帯を薄く塗る
  - **X軸ラベル**: 両端だけでなく途中にも等間隔で日付目盛りを出す(共通ヘルパー `xAxisTicks`。端はプロット外へはみ出さないアンカーにする)
  - **目標ラインのラベルはカード見出しの凡例が担い、グラフ内には出さない**(縦軸目盛りとの重なりを避ける)
- 体重推移グラフ
  - 1日1値(後勝ちで確定した値)を折れ線表示
  - 切り替え: 期間(週/月/全期間)
  - **縦軸レンジは実測体重だけから決める**(目標体重を含めると実測が上端に圧縮され傾向が読みにくくなるため)。目標線はレンジ内に収まる場合だけ破線で描き、範囲外(減量中で目標が下方に離れているなど)のときは右上の「目標◯kg」ラベルのみで示す。目標までの残距離は上部の進捗バー(下記)が担う
- 体脂肪率推移グラフ
  - 体重推移グラフと同様、1日1値を折れ線表示。体重グラフの直下に並べて表示する
  - 体脂肪率は任意入力のため、未記録の日は欠損(グラフ上は線を繋げない)として扱う。連続して記録がある区間ごとに線・面塗りを描く
- カロリー推移グラフ(日別の摂取カロリー合計、目標ラインを破線で重ねて表示)
- PFC推移の表示要否・表示形式(積み上げ棒グラフ等)は今後検討(12章参照)
- 水分推移グラフ(日別摂取量合計、目標ラインを破線で重ねて表示。記録の無い日は0mlで埋める。5章参照)
- 歩数・睡眠時間グラフ(Garmin由来の日別値。Issue #82)。活動記録が1件も無い(Garmin未連携)場合はカードごと非表示。データが無い日は0で埋め、睡眠は時間(h)単位で表示。目標ラインは持たない
- 棒グラフ(カロリー・水分・歩数・睡眠)の未記録日(0)は、実際に少なかった日と見分けられるよう淡い破線スタブで示す(Issue #128)
- 血圧グラフ(フェーズ4、Issue #117)。手書きSVGで最高・最低の上下2本線と、その間の帯(脈圧)を薄く塗って表示。記録が1件も無ければカードごと非表示
- おなか周りグラフ(サイズ(周囲径)の腹囲。フェーズ4、Issue #118)。手書きSVGの折れ線。点が疎(月1)でも破綻しないよう、記録が1点のときは線・面塗りを引かず点のみ描く。低頻度のため期間フィルタに関わらず常に全期間を表示する。記録が1件も無ければカードごと非表示
- 目標までの進捗表示
  - 画面上部に進捗バーを表示する(起点体重 → 目標体重を100%として、現在体重の到達度をバーで可視化。起点の決め方は9章参照)。バーには現在値と目標日までの残り日数を併記し、目標達成時はバーをaccent色にする(達成の瞬間の演出。デザインガイド参照)
  - 体重記録が1件もない場合は進捗バーの代わりに記録を促すメッセージを表示する
  - 現在のペースで目標日に到達しそうな体重の予測(起点→最新記録の傾きによる簡易線形予測。進捗バー内に表示。記録が少ない/期間が短すぎる場合は非表示。Issue #25)
- グラフ表示・履歴確認画面(8.1参照)・週次/月次レビュー(8.2・8.3参照)は、画面内の「グラフ/履歴/レビュー」サブタブ(セグメントコントロール)で切り替える(ナビゲーションのタブ数自体は増やさない)。レビュー内はさらに「週/月」サブタブで週次・月次を切り替える(8.3章)

### 8.1 履歴確認画面

- 推移画面のグラフ表示と対になる、記録の一覧確認用画面。推移画面内の「グラフ/履歴」サブタブとして実装する(ナビゲーションのタブ数自体は増やさない)
- 履歴内はさらに「体重」「食事」「水分」「筋トレ」「日記」「活動」「血圧」「サイズ」の種別サブタブで切り替える(体重・食事はIssue #31、水分・筋トレ・日記はIssue #73、活動はIssue #81、血圧・サイズ(周囲径)はIssue #117・#118。「サイズ」は周囲径記録の表示ラベル)。いずれも全期間・日付降順で表示し、From/To の日付絞り込みは全種別で共通に効く
  - 種別が8個と多く、等幅分割の `SegmentedControl` では各タブが潰れるため、この履歴の種別セレクタだけは**横スクロールのチップ列**(`ScrollableChips`)にする。各チップはラベル幅で、はみ出した分は横スクロールで到達する(選択中のチップは切り替えのたびに自動で見える位置へスクロールする)。項目が今後増えても破綻しない。グラフ表示・レビューの粒度切り替え(週/月)は項目数が少ないため従来どおり `SegmentedControl` のまま
- 推移グラフの期間切り替えとは独立して、全期間を日付降順(新しい記録が上)でリスト表示する
- リスト下部に「記録を追加」ボタン(食事マスタ・種目マスタの「手動で追加」と同じ破線ボーダーのトグル)を設け、入れ忘れた過去日の記録を新規に追加できる(活動記録を除く。Issue #141)。タップすると日付(食事のみ区分も)を選ぶインラインフォームが開き、選択中の種別に対応する記録画面へ`?date=`付きで遷移する。体重・血圧・サイズは日付が主キー(1日1件)のため、既存行タップ(編集意図)と区別する`create=1`フラグを付けて明示的に新規入力画面を開く。水分・筋トレ・日記・食事は元々`?date=`だけで未記録日でも新規入力画面が開くため、フラグは不要

**体重**
- 1行あたりの表示項目: 日付、体重、体脂肪率(未記録の日は「-」表示)、メモ(あれば日付の下に表示)。前日比の表示は任意(現時点では未実装)
- 各行をタップすると、その日の体重記録の編集画面に遷移し、体重・体脂肪率・メモを修正できる(3章の体重記録フローの編集版)。日時は記録のキーになっているため編集不可とする
- 水分・筋トレは日付ごとに集約した1日1行、日記は1日1件をそのまま1行で表示し、タップで各記録画面の該当日に遷移する(Issue #73)

**活動(Garmin由来。Issue #81)**
- 1日1行で歩数・総消費カロリー・睡眠時間(+睡眠スコア)を表示する(欠測項目は「−」)
- 他の種別と違い読み取り専用でタップ遷移なし — 真実の情報源はGarmin側(取り込みの仕組みはCLAUDE.mdのGarmin連携を参照)

**食事**
- ローカル日付ごとにグループ化し、日付見出し(日付・曜日・その日の合計カロリー)の下に、その日に記録した区分を朝→夜の順で1行ずつ並べる(記録フローと同じ「区分が単位」の見せ方。Issue #126)
- 1区分行あたりの表示項目: 区分アイコン・ラベル(朝食/昼食/夕食/間食)、品目数(「◯品」)、料理名のプレビュー(全品目名を「、」でつないだ1行)、区分の合計カロリー、未同期バッジ(区分内に未同期の品目があれば)。「食べなかった」として記録した区分は「◯品」の代わりに落ち着いた配色の「食べなかった」バッジのみを出し、料理名プレビュー・kcalは表示しない(4章「食べなかった」の記録・Issue #143)
- 各区分行をタップすると、その日のその区分の記録画面(`/record/meal?type=<区分>&date=<日付>`)に遷移し、記録フローと同じ画面でその区分の全品目をまとめて編集できる
- 食事は1日に複数件記録しうるが、現状は個人利用の規模(1日数件)で全期間を一括描画しても問題ないため、ページネーションは設けていない(体重履歴と同様。件数が増えた場合は将来検討)

- 週次データの集計は `WeeklyDigest`(11章・AIコンサルティング設計書参照)を生成する純関数として実装し、画面はその値を表示するだけにする。`WeeklyDigest` はAIコーチング(Issue #12)への入力契約と共通

  - **体重**: 週平均体重、前週比(週平均同士の比較。単日の値は水分等のノイズが大きいため使わない)、目標までの必要ペース(kg/週)との比較
  - **カロリー**: 週の平均摂取kcal / 目標kcal、目標達成日数(◯/7日)
  - **記録率**: 記録した日数/7日(Issue #46)
  - **PFC平均**: 目標値(9章)が設定されていれば「実績 / 目標」の対比表示(Issue #47)
  - **活動(Garmin)**: 週平均歩数・週平均総消費カロリー・平均睡眠時間・活動データがある日数(Issue #82)。週内に活動記録が無ければセクションごと非表示(Garmin未連携ユーザーに影響しない)
  - **活動量の変化(Issue #174)**: 当該週の平均歩数・筋トレ日数を、直近4週の平均と並べて表示する(歩数は変化率も併記)。実測TDEEの下落の要因が消費側にあることを示すためのセクション。比較できる過去週が2週未満の場合、および過去に歩数の基準も筋トレの実績も無い場合はセクションごと非表示。当該週の活動記録が5日未満の週は歩数の比較を行わず、その旨を注記する(欠測の多い週を「活動量が落ちた週」と誤って見せないため)
  - **血圧(フェーズ4、Issue #117)**: 週平均(最高/最低)・記録した日数・家庭血圧135/85以上だった日数・同じ週の週平均体重(体重×血圧を並べて見せる)。週内に血圧記録が無ければセクションごと非表示。医療機器ではないため事実の提示に留め医学的判断はしない旨を注記する。この `bloodPressure` セクションはAIコーチング入力(WeeklyDigest)にも含まれ、AIにも同じ免責(血圧値の医学的評価・受診勧奨を禁止)を課す
  - **筋トレ**(Issue #103): 記録した日数・種目数・総セット数。週内に筋トレ記録が無ければセクションごと非表示
  - **水分**(Issue #103): 記録がある日の平均摂取量(記録の無い日は分母に入れない)、目標達成日数(目標未設定なら非表示)、記録した日数。週内に水分記録が無ければセクションごと非表示
  - **この週の日記**(Issue #103): 週内の日記(日付・気分タグ・飲酒タグ・本文)をローカル表示する(digestとは独立に取得。表示自体はAI送信オプトインと無関係)。カード下部に、本文がAIコメント生成に渡る状態かどうか(設定「日記の本文をAIに送る」のON/OFF)を常に注記する。日記が無い週は非表示
  - **実測消費カロリー(実測TDEE)**: 逆算値と、それに基づく目標カロリーの補正提案(Issue #44。有効週が無い間は「データ蓄積中」表示)。Garminの週平均総消費があれば併記し、両者の乖離が15%を超える週は「食事の記録漏れ等の可能性」の注記を出す(独立した2つの推定値の一致度を記録の信頼度の目安にする。Issue #82)。**摂取が基礎代謝を下回り(`INTAKE_BELOW_BMR`)、かつ活動量も落ちている(`ACTIVITY_DROP`/`WORKOUT_STOPPED`)週は、補正提案の直下に「摂取を削る余地はなく、消費側の回復が必要」という注記を出す**(Issue #174)。この状況では提案値が基礎代謝でクランプされるため、注記が無いと「さらに食べる量を削れ」としか読めず判断を誤らせる
  - **クロス分析**(Issue #112): 週内データの掛け合わせ集計(`WeeklyDigest.crossAnalysis`)を事実の提示スタイルで表示する。週単位はサンプル数が少なく「相関」とは言い切れないため、断定・解釈はせず「睡眠6時間未満の日が2日あり、その日の平均摂取カロリーは2,050kcal(それ以外の日は1,770kcal)でした」のような事実文に留め、解釈はAIコメントに委ねる。カード下部に「日数が少ないため差は偶然の範囲のこともある」旨を常に注記する。項目は3つで、比較が成立する項目だけ表示し、1つも無い週はカードごと非表示:
    - **睡眠×食事**: 睡眠6時間未満の日とそれ以外の日の、同じ日の摂取カロリー比較。Garminの睡眠時間は「その日の朝までの夜間睡眠」のため、同日ペアリングが「睡眠不足明けの日の食事」を意味する(翌日ペアリングにしない。意思決定ログ参照)。睡眠不足の日に食事記録が無い週は非表示
    - **気分×食事**: 気分が良い日(絶好調・良い)と眠い・不調の日の摂取カロリー比較。両群に食事記録のある日が無い週は非表示
    - **飲酒×食事**: 飲酒タグ(6章)のある日の日数と、当日・それ以外の日・翌日(週内のみ)の平均摂取カロリー。「それ以外の日」はタグの無い日全体であり「飲酒なしと記録した日」ではない。飲酒日が無い週は非表示
  - **警告フラグ**: ペースが速すぎる(週あたり体重の1%超)、平均摂取が基礎代謝未満、記録率の低下など。コード側で判定した結果を表示する(AIの判断に依存しない)
  - **SNS共有カード**(Issue #235): その週の数字をカード画像として書き出す導線(AIコメントの下)。仕組み・載せる数字の決め方は2.1章と共通。載せられる数字が1つも無い週は非表示
  - **AIコーチのコメント**(Issue #12、このセクションのみAIを使う): 「生成する」ボタンで週の総評・良かった点・来週のアクションを生成し、`AdviceRecord`(11章)としてキャッシュする。生成済みの週はキャッシュを表示し、再生成ボタンを設ける

**ビジュアルデザイン**: 2026-07-07、Claude Design製のフェーズ2プロトタイプ(`docs/archive/handoff_lifelog_app/prototype.dc.html`)のトンマナに合わせてモックアップを作成し確認済み([Artifact](https://claude.ai/code/artifact/380bd9e4-d0cf-4665-bebd-cd5b7569ae9b))。実装時はこのモックアップのコンポーネントパターン・配色を踏襲する。要点:

### 8.3 月次レビュー画面(フェーズ3)

※実装状況: 実装済み(Issue #114。2026-07-14)。画面は `src/pages/trends/MonthlyReview.tsx`(AIコメント欄は同 `MonthlyAdviceCard.tsx`)、集計は `src/db/monthlyReview.ts` → `src/lib/monthlyDigest.ts`。クロス分析カードは週次と共有(`CrossAnalysisCard.tsx`)。

- 週次レビュー(8.2章)は「今週の達成→来週のアクション」という行動を変えるレビューとして機能する一方、ペースの加速・減速や目標までの残距離といった**高度を上げた俯瞰**は週の粒度では見えない。そこで月次ならではの内容に絞った月次レビューを追加する(Issue #114)。**週次のカードを30日窓で並べ直すのではなく、内容を月次向けに絞る**
- **UIはサブタブを増やさず、レビュータブ内に「週/月」の切り替え**(`SegmentedControl`)を置く。「週」で週次レビュー(8.2章)、「月」で月次レビューを表示する。デフォルトは「週」。月ナビゲーション「◀ / ▶」で前月・翌月に切り替えられる(今月表示中は翌月へ進めない)
- **月の定義**: 暦月は月曜始まりの週と端が揃わないため、**「その月に日曜(週の終わり)が含まれる月曜始まりの週の集合」**とする(4〜5週)。週を分割せず日曜の属する月へ丸ごと割り当てるため、全ての週がちょうど1つの月に属する(隣接月と重複・欠落しない)。例: 2026年7月は6/29週(日曜7/5)〜7/20週(日曜7/26)の4週で、期間は6/29〜7/26。7/27週(日曜8/2)は8月に属する。実装は `src/lib/date.ts` の `weekStartsOfMonth`(経緯は意思決定ログ)
- 月次データの集計は `MonthlyDigest`(11章・AIコンサルティング設計書参照)を生成する純関数として実装し、画面はその値を表示するだけにする。週次の集計関数(週次TDEE逆算・クロス集計)を再利用する。`MonthlyDigest` はAIコーチング(月次版)への入力契約と共通
- 表示セクション(データ不足のセクションは非表示にして段階的に見せる):
  - **体重(週平均の推移)**: 月内の週平均体重を折れ線(4〜5点)で表示し、ペースの加速・減速を見せる。単日ではなく週平均同士を比較する8.2章の設計思想を延長する。折れ線は手書きSVG(他グラフと同じ方針)で、記録が無い週は点を打たず隙間にする。月間変化(記録がある最初の週と最後の週の週平均の差)・平均ペース(kg/週)・体重を記録した週数を併記する
  - **目標へのマイルストーン**: 目標日までの残り期間、必要ペース(kg/週)、**今月のペースを維持した場合の目標日時点の到達見込み体重**。見込みが目標を上回る/下回るで順調・要注意を色分けする
  - **実測消費カロリー(月間推定)**: 月窓での実測TDEE。週単位の逆算はブレが大きいため、月内の全有効週の週次逆算値を平均した安定値を出し、週ごとの逆算値の幅(最小〜最大)も併記する。目標カロリー補正提案(#44)の信頼度を上げる材料になる(有効週が無い間は「データ蓄積中」表示)
  - **カロリー・記録**: 月内の平均摂取kcal / 目標、目標以内の日数(◯/月の総日数)、食事を記録した日数、記録率(体重または食事)
  - **血圧(月次。フェーズ4、Issue #117)**: 月平均(最高/最低)・記録した日数・家庭血圧135/85以上だった日数。週内に記録が無ければ非表示。週次と同じく事実の提示に留め医学的判断はしない。月窓は週次よりサンプルが多く、体重×血圧の傾向が安定して見える(月次では週平均体重の併記はせず、体重の推移は上部の体重セクションで見せる)
  - **クロス分析(月間)**: #112の集計を月窓で再実行する(`CrossAnalysisCard` を週次と共有)。週次より標本数が多いため、注記は「週次より日数が多いぶん傾向の目安になるが、因果の断定はできない」旨に変える。項目(睡眠×食事・気分×食事・飲酒×食事)と非表示条件は週次と同じ
  - **警告フラグ**: 週次と同じ語彙(ペース過剰・摂取が基礎代謝未満・ペース不足・記録率低下・体重記録なし・データ不足)を月窓の閾値で判定する。記録率低下は「これまでに経過した日数(進行中の当月は今日まで、完了済みの月は総日数)の7割未満」で判定する(月全体を分母にすると当月の序盤に毎日記録していても常に立ってしまうため)。データ不足は「記録した日が7日未満(1週間分未満)」

## 9. 設定画面

- 目標体重・目標日付の設定(**初期値は持たない。** 未設定の状態がありうる。Issue #217)
  - 目標体重・目標日・1日の目標カロリーは既定値を持たず、ユーザーが設定するまで「未設定」として扱う
  - 未設定の項目は各画面で行・凡例ごと非表示にする(0kgや1kcalのようなダミー値を代入しない)。詳細は9.1節
- 基準日の設定(進捗バー用)
  - 進捗バーの起点となる日付を1つ設定する(初期値: 未設定。ダイエット開始日など任意の日付をユーザーが選択)
  - 基準日当日の体重記録が存在すればその値を起点(0%地点)とする。基準日が未設定の場合や、基準日当日の記録が存在しない場合は、**一番古い体重記録を起点にフォールバックする**(12章にあった論点は決定済み)
  - 進捗バーは 推移画面 に表示する(基準日体重 → 目標体重を100%として、現在体重の到達度をバーで可視化。8章参照)
  - 体重記録が1件もない場合は進捗バーを表示せず、記録を促すメッセージを表示する
- 身体プロフィールの設定(フェーズ3、Issue #43)
  - 身長(cm)・生年・性別・活動レベル(5段階: 活動係数 1.2 / 1.375 / 1.55 / 1.725 / 1.9)を入力する
  - 目標カロリー・PFC目標の自動計算にのみ使う。未入力でも従来どおり各目標値の手動入力は可能
  - 設定画面の「目標」カードの上に「あなたのプロフィール」セクションとして新設する。行のUIは既存の目標体重・目標日と同じアイコンタイル+ラベル+値+シェブロンのパターンを踏襲する([Artifact](https://claude.ai/code/artifact/380bd9e4-d0cf-4665-bebd-cd5b7569ae9b)参照)
- 1日の目標摂取カロリーの設定(手動入力に加え、フェーズ3で「自動計算」ボタンを追加。Issue #43)
  - 自動計算ボタン: 身体プロフィールからMifflin-St Jeor式で基礎代謝→推定TDEEを計算し、`推定TDEE − 必要日次赤字((現在体重−目標体重)×7700÷残り日数)` を提案値として表示する。ユーザーが確定したら反映する(**自動で上書きしない**)
  - 提案値が基礎代謝を下回る場合は警告して基礎代謝でクランプ、必要ペースが週あたり体重の1%を超える場合は警告を表示する
  - 実測TDEE(Issue #44)が得られている場合は、計算式ベースの値より実測ベースの提案を優先して表示する
  - タップで開く自動計算シートは、計算根拠(基礎代謝→活動レベル→実測優先の消費カロリー→必要ペース)を行で見せたうえで提案値とガードレールの判定結果を表示し、「この値を目標にする」の確定操作を経て初めて反映する(既存の目標編集ボトムシートと同じ構造。Artifact参照)
### 9.1 初回セットアップ(Issue #217)

開発者本人の目標値を `DEFAULT_SETTINGS` から撤去したことに伴い、目標が未設定のまま起動したユーザーを受け止める画面を `/setup` に置く。

- **誘導**: ホーム表示時に「目標3項目が未設定」かつ「スキップ済みでない」なら `/setup` へ置換遷移する。判定は `isInitialSetupComplete()` / `shouldShowInitialSetup()`(`src/db/settings.ts`)に集約し、**ホームと初回セットアップ画面で必ず同じ関数を使う**(条件が割れると、片方だけ満たしたユーザーがどちらの画面からも抜けられなくなる)
- **必須は目標3項目のみ**(目標体重・目標日・1日の目標カロリー)。身体プロフィール・PFC目標・目標水分量は任意で、未入力でも先へ進める — これらは自動計算や補助表示にしか使わず、無くても記録・進捗表示が成立するため
- **レイアウト**: 記録フロー画面と同じ全画面構成(下部ナビ非表示 + 下部固定バー)。ナビを出すと目標未設定のまま他タブへ素通りできてしまうため、`App.tsx` の全画面フロー判定に `/setup` を含める
- **入力UI**は設定画面と同一の `SettingRow` + `ValueEditorDrawer` / `PfcEditorDrawer` を再利用する。同じ項目を2通りの操作で入力させない
- **完了しても自動遷移しない。** 離脱は「はじめる」(必須が揃うまで非活性)と「あとで設定する」の明示操作だけ。自動遷移させると、最後の必須項目を埋めた瞬間に任意項目へ触れないまま画面から追い出される
- **各項目は編集シートで確定した時点で保存される**(設定画面と同じ)。「はじめる」は保存操作ではなく離脱操作であり、入力途中で離脱しても入れた値は失われない
- **必須が揃ったら「あとで設定する」は出さない。** 上記のとおり値は保存済みのため、その状態の「あとで」は「はじめる」と同じ動きになり、押した人に「入力が破棄されるのか」と思わせるだけになる。押せる出口は常にどちらか一方だけにする(`initialSetupSkipped` の意味も「目標を入れずに先へ進んだ」に保たれる)
- **「あとで設定する」**は `Settings.initialSetupSkipped` を立ててホームへ戻る。既存ユーザーの移行経路であり、これが無いとホームが毎回セットアップへ差し戻して記録を始められない。この項目は端末ごとの状態のためシート同期の対象外(`apiToken`・`lastSyncedAt` と同じ扱い)
- **目標未設定時の各画面の振る舞い**
  - ホームのカロリーカード: 目標バッジ・残りkcal・進捗バーを出さず、摂取実績のみ表示
  - 推移(グラフ): 体重グラフの目標線と凡例、カロリーグラフの目標線と凡例を出さない
  - 推移(進捗バー): 目標体重・目標日が揃っているときだけ表示
  - 週次・月次レビュー: 必要ペース行、目標との対比(`/ 目標 xx`)、目標以内の日数を出さない。月次の「目標へのマイルストーン」カードは目標日が無ければカードごと非表示
  - AIコーチング: digestの `goal.*` と `calories.targetKcal` / `daysOnTarget` を `null` で渡す。**ダミー値を入れないこと** — digestはそのままプロンプトへ渡るため、0kgや1kcalを入れるとAIがそれを実在の目標として助言し、その助言はシート同期される(再生成しても同じものは出ない)
  - 目標カロリーの自動計算: 目標体重・目標日のどちらかが欠けていれば実行せず、何が足りないかをヒントに出す

- PFC目標値の設定(3項目、g/日。フェーズ3、Issue #47)
  - 3つの数値入力欄+「自動計算」ボタン。自動計算の初期値: たんぱく質 = 直近体重×2.0g、脂質 = 目標カロリー×25%÷9、炭水化物 = 残余((目標kcal−P×4−F×9)÷4)。提案→確定の流れは目標カロリーと同様(自動で上書きしない)
  - 目標摂取カロリーを変更した際は再計算を提案する
- 1日の目標水分摂取量の設定(ml、手動入力、初期値未設定。5章参照)
- AIコーチング: 「日記の本文をAIに送る」トグル(`Settings.sendDiaryTextToAi`、初期値OFF。Issue #103でIssue #12を決着)
  - ONにすると、週次レビューのAIコメント生成時にその週の日記本文が `WeeklyDigest.diaryEntries` としてGoogle Gemini APIへ送られる。OFFの間は従来どおり気分タグの件数集計のみ(AIコンサルティング設計書7章)
  - トグルの下に送信範囲の説明文を常設する
- 食事マスタ管理画面への導線(登録件数を併記。画面自体は4.1章参照)
- 種目マスタ管理画面への導線(登録件数を併記。画面自体は7.1章参照)
- 習慣マスタ管理画面への導線(登録件数を併記。フェーズ4、Issue #113)。習慣(名前・任意の週あたり目標頻度)の一覧・追加・編集・アーカイブ(休止)・削除を行う。食事マスタ・種目マスタと同じ構成
- データ同期・バックアップ(スプレッドシート)
  - 「今すぐ同期」ボタン(手動同期のトリガー。押下時は同期中であることが分かるようローディング表示)
  - 最終同期日時の表示
  - 未同期件数の表示(任意、あれば同期の必要性が分かりやすい)
  - 同期失敗時はその旨をエラーメッセージとして表示し、次回同期のタイミングで自動的に再試行する
  - 「シートから取り込み(復元)」ボタン(Issue #54。スプレッドシートの全記録をアプリに取り込む。押下時はローディング表示、完了時に取り込み件数・スキップ件数を表示。失敗時は「ローカルの記録は変更されていない」ことを明示する。取り込みの仕組みは10章参照)
- 完全バックアップ(ファイル)(Issue #164)
  - **シート同期では戻せないデータを埋めるための経路。** 記録・設定・AIコメントはシート同期で戻せるようになったため(#164)、シートから戻らないのは**食事のAI推定値・写真参照と`apiToken`だけ**。位置づけは日常の保全ではなく、機種変更・ドメイン移行の前に断面をまるごと退避する保険
  - 「JSONファイルに書き出す」ボタン: `syncDeletions`・`googleAuth` を除く全テーブルを1つのJSONにまとめてダウンロードする。ファイル名は `karadalog-backup-YYYY-MM-DD.json`。完了時にテーブルごとの件数を表示する
  - 「JSONファイルから復元」ボタン: ファイルを選ぶと**その場では復元せず**、書き出し日時・取得元オリジン・テーブルごとの件数を提示して確認を求める。「置き換える」で実行、「やめる」で取り消し
  - **復元は全テーブルを削除してから書き戻す**(機種変更・ドメイン移行を想定した完全な置き換え)。取り消せないことを警告として明示する
  - 壊れたファイル・バックアップでないJSON・全テーブルが空のファイルは復元前に弾き、「端末のデータは変更されていません」と明示する。**検証を通さずに全削除してしまうと復旧できないため、パースと検証は削除より先に行う**
  - `syncDeletions`(削除トゥームストーン)はバックアップに含めず、**復元時には復元先に残っていたぶんも消す**。同期の途中状態であって利用者のデータではないため。持ち越すと、次の同期で復元したレコードに対応するシートの行が `deleteDimension` で消され、復元レコードは `synced: true` のため再送信もされず**シート側から恒久的に失われる**。書き出し前に「今すぐ同期」を済ませれば保留中の削除はシートへ反映される
  - `googleAuth`(Googleのrefresh token。Issue #214)もバックアップに含めない。**認証情報を持ち出せるファイルにしない**という判断で、復元後はGoogleと連携し直す(連携はもともと端末ごとに行うものなので、機種変更時はいずれにせよやり直しになる)
  - **書き出したファイルには `Settings.apiToken` が平文で入る。** 完全な復元を優先して除外はしないが、共有ストレージに置かないよう画面上で警告する
  - **IndexedDBはオリジン単位のため、アプリの配信URLが変わると同じブラウザでもデータは引き継がれない。** 機種変更・ブラウザデータ削除に加え、ドメイン変更の前にも書き出しが必要
- 機種変更・ドメイン移行の手順(Issue #164。2026-08-08に実データでリハーサル済み)
  - **移行前**: 移行元の端末で「今すぐ同期」→「JSONファイルに書き出す」。同期を先にするのは、保留中の削除トゥームストーンをシートへ反映しきってから断面を取るため
  - **移行後**: 新しい端末・新しいURLで**「JSONファイルから復元」だけを行う**。JSONはシートの内容を完全に包含し、さらにシートに無い食事のAI推定値・写真参照・`apiToken` まで含むため、これ1回で完結する
  - **「シートから取り込み」→「JSONから復元」の順で実行してはいけない。** 復元は全テーブルを削除してから書き戻すため、先に取り込んだ内容は捨てられる。逆順(復元→取り込み)なら安全だが、JSONが最新であれば取り込む必要は無い
  - JSONを失った場合の代替経路は「APIトークンを手入力 → シートから取り込み」。この場合は食事のAI推定値・写真参照が戻らない
  - 事前の保険としてスプレッドシートを複製しておくとよい(移行時の押し出しが暴発した場合の巻き戻し先)。移行完了後は複製を削除する — 残すとどちらが正か分からなくなる
  - ドメイン移行の場合は、移行後に新URLでPWAをホーム画面に追加し直し、旧URLのPWAを削除する
- トラブルシューティング: 「アプリのリセット」(Issue #203)
  - **Service Workerとキャッシュだけを捨てて取り直す操作。記録・設定(IndexedDB)には一切触れない。** 2026-08-09、インストール済みPWAのService Workerが壊れて `/api/*` への通信が全て失敗した際、アプリ側にSWを扱うコードが無く、復旧手段が「PWAの再インストール」しかなかった。Android Chromeではアンインストールでサイトのストレージごと消えることがあり、記録が全てIndexedDBにある本アプリでは危険な操作になるため、**再インストールせずに同じ復旧を行える経路**として用意する
  - 実行前に確認を挟み(「アプリを再読み込みします。未同期の記録は端末に残るため失われません」)、確定後はSWの登録解除+Cache Storage削除→リロードまでを行う
  - SW登録解除とキャッシュ削除は片方が失敗しても、もう片方を最後まで実行する(壊れた状態からの復旧手段のため、一部でも捨てられたほうが成功率が上がる)。両方失敗して何も捨てられなかった場合だけエラーを表示する
- **Googleとの連携(Issue #214。配布版 #213 の一部)**
  - 「Googleと連携する」ボタンでGoogleの認可画面へ遷移し、戻り先の `/oauth/callback` で認可コードをトークンへ交換する。連携済みなら連携日時と「連携を解除する」を出す
  - カードに**要求スコープの説明を常設する**: 「このアプリが作成したファイルにしかアクセスできません(Driveの他のファイルは見えません)」。配布時に相手へ説明する要になるため、画面にも書く
  - **端末ごとに連携が必要**(認可情報は端末ローカル)。その旨と「バックアップにも同期先シートにも含まれない」ことをカード下に注記する
  - 連携はこの時点では**同期には使われない**(Sheets APIのクライアント直呼び出しは #215、シートの新規作成は #216)
- APIトークンの設定(Issue #87)
  - Worker API(`/api/*`)を第三者の呼び出しから守る共有トークン。Workerのシークレット `API_AUTH_TOKEN` と同じ値をテキスト入力で設定し、全API呼び出しの `Authorization: Bearer` ヘッダとして送られる
  - 一覧上は値そのものは表示せず「設定済み / 未設定」のみ表示する。空欄で保存すると未設定に戻せる
  - Worker側の `API_AUTH_TOKEN` が未設定の間は認証を要求しない(ローカル開発と、シークレット登録→クライアント設定完了までの移行期間のため)。トークン不一致時のAPIは401を返し、設定画面の確認を促すエラーメッセージが各画面の既存エラー表示に出る
- 同期先スプレッドシート(Issue #216)
  - 「データ同期・バックアップ」セクションの先頭に置くカード。状態は「未作成 / 作成済み」の2つだけ
  - 未連携なら「先にGoogleと連携してください」と案内し、連携済みで未作成なら「スプレッドシートを作成」ボタンを出す。作成済みなら「シートを開く」(Google Sheetsを新規タブで開く)
  - **スプレッドシートIDの手入力欄は置かない。** `drive.file` スコープはアプリが作成したファイルにしかアクセスできず、他所で作られたシートのIDを入れてもGoogleが403を返すだけのため
  - **作成直後に全レコードを未同期へ戻す。** 新しいシートは空なのに手元のレコードは送信済みのままで、そのままでは1件も書き出されない。戻したうえで「今すぐ同期」を押せば、手元の記録がそのまま新シートに載る
- プライバシーポリシー(Issue #238)
  - 「このアプリについて」セクションから `/privacy` へ遷移する読み物の1画面。下部ナビは出さず、ヘッダーの戻るで設定画面へ返る
  - **OAuth同意画面(#214)を本番公開するには、プライバシーポリシーURLの登録が必須**。Google Cloud Console には `https://lifelog.n1lab.workers.dev/privacy` を登録する。配布(#213)の相手に「何が端末に残り、何が外へ出るか」を示す場所も兼ねる
  - 構成は「まとめ(4行)→ 端末に保存される情報 → シートへの同期 → Google連携 → AIに送られる情報 → 行わないこと → データの削除 → 連絡先」。**AIに送られる情報だけは表**にする(誤解が起きやすいのはここだけのため)
  - **本文は実装と1対1で対応する事実だけを書く。** 日記本文の送信は `Settings.sendDiaryTextToAi` のオプトイン時のみ、スコープは `drive.file` のみ、写真は保存しない — この3点を変えたら本文も直す
  - 連絡先はGitHubのIssue。**個人のメールアドレスは載せない**(公開ページのため)。同意画面のサポートメールはGoogle Cloud Console側に登録する別物

## 10. データ同期フロー

同期は「ローカルファースト」を維持したまま、ネットワーク接続時にローカルの変更(新規・編集・削除)をスプレッドシートへ書き出すための一方向(アプリ→スプレッドシート)の仕組みとする。これに加えて、シート→アプリ方向の**手動取り込み(インポート)**を持つ(Issue #54。10.1章参照)。常時双方向同期にはしない。ただし例外として、Garmin由来の**活動記録タブだけ**は自動同期のたびにシートから取り込む(Issue #133。10.2章参照) — 活動記録はアプリ内に編集・削除が無くGarminが真実の情報源で、競合が起きないため。

※実装状況: 実装済み(Issue #3、削除・編集の反映はIssue #30、取り込みはIssue #54、水分・筋トレ・日記の追加はIssue #72、食事マスタ・種目マスタの追加はIssue #96)。クライアント側の同期エンジン(未同期レコード・削除トゥームストーンの抽出、部分成功のハンドリング、失敗時の未同期維持、起動時/手動のトリガー)に加え、送信先となるGoogle Sheetsへのトランスポートも実装済み(Issue #215でWorker経由をやめ、クライアントから直接Sheets APIを叩く形になった)。

1. トリガー
   - アプリ起動時: オンライン(`navigator.onLine` で判定)であれば、起動直後にバックグラウンドで未同期レコードの同期を自動的に試みる(ユーザー操作は不要)
   - アプリ復帰時・オンライン復帰時(Issue #105): PWAをホーム画面から開き直したときの再表示(`visibilitychange`)と、オフライン→オンライン復帰(`online`イベント)でも同期を試みる。タブ切り替え等での連続発火を防ぐため自動トリガーには最小間隔(5分)のスロットリングと実行中の再入抑止を設ける(`src/sync/autoSync.ts`)。オンライン復帰は「同期が可能になった」明確なシグナルのため最小間隔を待たずに実行し、オフラインでスキップした試行は間隔に数えない
   - 手動: 設定画面の「今すぐ同期」ボタンから、いつでも明示的に同期を実行できる(スロットリングの対象外)
2. 対象データ
   - `synced: false` の体重記録・食事記録・水分記録・筋トレ記録(セットレコード)・日記記録・食事マスタ・種目マスタ・血圧記録・周囲径記録・習慣マスタ・習慣記録(新規・編集分)を対象とする(差分同期。全件送信は行わない)。マスタも同期対象とするのは、記録と違いバックアップ手段が他に無く、シート直接編集による一括登録の受け口を兼ねるため(Issue #96。#14の残課題を引き継いだもの)。血圧・周囲径・習慣はフェーズ4の追加(Issue #117・#118・#113)
   - 加えて、同期済みの可能性がある記録を削除した際に残す**削除トゥームストーン**(`syncDeletions` テーブル。削除対象のタブとID列の値を保持)も対象とする。編集は`synced`が`false`に戻ることで、削除はトゥームストーンによって、それぞれ次回同期で拾われる(Issue #30)
   - 筋トレは「その日の全セットをまるごと置き換え」という保存方式(7章参照)のため、置き換えのたびに全セットへ新しいIDを振り直す。そのため置き換え前の全セットIDを削除トゥームストーンとして残し、シート側の古いセット行を次回同期で消す(Issue #72)。結果として1回の保存が「その日の既存行を全削除→新規行を全追記」という比較的重い同期になるが、他の記録と同じupsert/削除の仕組みをそのまま流用できる
3. 送信先
   - **Google Sheets APIをクライアントから直接呼び出す**(Issue #215。Workerは経由しない)。同期先は**アプリが利用者自身のGoogle Driveに新規作成したスプレッドシート**(Issue #216。今使っている手動運用の既存スプレッドシートとは別物)
   - **タブの一覧・タブ名・ID列・列の並びは `src/sync/sheets/sheetsSync.ts` が正**(`*_CONFIG` がタブ名とID列、`*_HEADER` が自動作成タブの見出し行、`*ToRow` が列の並び)。本書はここに個々の列を再掲せず、**コードからは読み取れない「なぜその形なのか」だけ**を以下に残す(同じ数値を2箇所で持つと必ずズレるため。Issue #194)
   - 反映は行末尾ID列をキーにした**upsert + 削除**で行う(Issue #30):
     - 新規(ID列に無い): `values.append` で末尾に追記
     - 編集(ID列に既に有る): `values.get` でID列を読んで行番号を特定し、`values:batchUpdate` で該当行を上書き(編集のたびに新しい行が増えて重複するのを防ぐ)
     - 削除(トゥームストーン): 同じくID列で行を特定し、`batchUpdate` の `deleteDimension` で行を物理削除する(複数行は行番号の降順で削除し、行番号ズレを避ける)。ID列に該当行が無ければ「削除済み」とみなして冪等に成功扱いにする
     - **日付・日時はJST表示の文字列に変換して書き込む**(日付は`yyyy年mm月dd日`、日時は`yyyy年mm月dd日 hh:mm`)。シートを人間が読む閲覧用の写しとして成立させるため
     - **タブの自動作成**: シートの新規作成時に全タブを `*_HEADER` の見出し行付きで作る(Issue #216)。後から増えたタブも、同期時に無ければ同じ形で自動作成する。**記録5タブが手動作成前提だったのは #216 まで** — 他人のDriveにアプリがシートを作る以上、手動作成の前提は成立しないため。**活動記録タブだけはアプリが作らない**(Garmin側が作る側で、列構成の正が `scripts/garmin/` にあるため)
     - **後付けの列はID列より後ろに置く**(日記の飲酒列=#112、種目マスタの部位列=#104)。既存シートのID列の位置を動かすと、それまでに書かれた行のupsert・削除が効かなくなるため。この2タブだけ取り込みの読み取り範囲をID列ではなく `lastColumnLetter` まで広げている
     - **設定タブは1設定=1行の key-value 形式**(#164)にして、設定項目が増えても列構成を変えずに済ませる。**`apiToken` と `lastSyncedAt` は書き出さない**(前者は取り込みAPIの認証に使うためシートからは原理的に復元できず、後者は端末ごとの同期状態)。真偽は「はい/いいえ」で書く(`USER_ENTERED` による解釈し直しを避けるため)。取り込みは**ローカルで未設定の項目だけを埋める**(上書きすると機種変更後に入れ直した値を潰しうる)
     - **AIコメントの判定・配列の書き方**(#164): 判定は `WeeklyAdvice.verdict` を日本語ラベル(順調/やや遅れ/遅れ/要注意。画面のバッジと同じ語)に変換して書き、取り込み時に逆引きする。良かった点・来週のアクションは配列なので**1セル内の改行区切り**で並べる。**生成時の `digest` は書き出さない** — レコードから再計算でき(`getWeeklyDigest()`)、画面のどこからも参照していないため。1セルにネストしたJSONを詰めると「人間が読める閲覧用の写し」という利点を損なう
     - **月次AIコメントは月キー(YYYY-MM)をそのままセルに書かない**(#164)。`valueInputOption: USER_ENTERED` ではSheetsが「2026-07」を日付(月初)へ解釈し直してしまい、以後のupsertがID列で既存行を見つけられず再生成のたびに重複行が増える。表示列は漢字入りの「2026年07月」(解釈されない形)、ID列は体重記録と同じフル日付「2026-07-01」にし、月キーとの間で変換する(`monthToSheetLabel`/`monthToSheetId`)
     - **AIコメントの2タブには削除の仕組みを設けない。** アプリに削除UIが無く、再生成は同じキーへの上書き(upsert)で足りるため、削除トゥームストーンの対象にしていない
     - **日記の本文はそのままシートに書き出す**(#72)。プライバシー面は認識した上で、バックアップの完全性を優先する判断とした
     - **習慣記録のIDは `${日付}_${習慣ID}` の合成キー**(#113。1日1習慣1件の後勝ち)。習慣名はシートの可読性のための非正規化コピー
     - **種目マスタの部位は日本語ラベルで書き出し、取り込みは日本語ラベル・英語キーのどちらも受け付ける**(#104。空・未知の値は「分類なし」として行自体は取り込む)
     - **JST変換は`Intl.DateTimeFormat`に`timeZone: "Asia/Tokyo"`を明示して行う**(`Date`の`getHours()`等をそのまま使うと、端末のタイムゾーン設定次第でズレる。Worker上で動いていた頃はUTC固定だったため必須だったが、クライアントへ移設した後も端末側の設定に依存させない意味で維持する)
     - 既存の手動運用シートは「1日1行、その日の食事の合計カロリー/PFC」という集計形式でアプリの`MealRecord`(1食事=1レコード)とは粒度が異なるため、あえて合わせずに新規シートとした
   - 認証は**利用者自身のGoogleアカウント**(Issue #214)。access tokenはメモリ、refresh tokenは `googleAuth` テーブルに置く。**サービスアカウントは使わない**(Issue #215で廃止。Garmin連携だけは別経路で今も使う)
4. 成功時
   - 送信(追記/上書き)を確定した記録の`synced`フラグを`true`に更新し、削除を確定した行の削除トゥームストーンを消す。最終同期日時(`lastSyncedAt`)を更新する
5. 失敗時(オフライン、APIエラーなど)
   - `synced`フラグは`false`のまま維持し、削除トゥームストーンも残す。記録自体は失わない
   - 次回のトリガー(アプリ起動時 or 手動)で再度同期を試みる
   - ユーザーには軽くエラーであることを伝える(派手なエラー画面は出さない)。設定画面のメッセージ表示以上の通知(バックオフ間隔・ホーム画面バッジ等)は追加しない(12章参照)
   - **エラー表示は「サーバーに届かなかった」と「サーバーがエラーを返した」を区別する**(Issue #204)。前者(接続不成立・タイムアウト)はユーザー側の対処(通信環境の確認・9章「アプリのリセット」)が要り、後者(Gemini APIエラー等)は待てば直りうるため、必要な行動が違う。区別は `/api/*` を叩く共通処理(`src/api/request.ts`)が担い、接続不成立とタイムアウトを `ApiConnectionError` として投げ分ける。2026-08-09の障害でブラウザ生の "Failed to fetch" がそのまま画面に出て切り分けに難儀した反省による
   - **`/api/*` の呼び出しにはタイムアウトを設ける**(Issue #205)。応答が返らないまま処理中の表示が続くと、ユーザーは失敗か処理中かを判別できないため。AI生成(週次・月次コメント、食事写真判定)はWorker側で1回リトライしうるぶん長め、同期・取り込みは短めに取る(具体値は `src/api/request.ts` が正)
   - **Worker側のGemini呼び出しのリトライは、一時的な失敗に限る**(Issue #205)。再試行するのは 5xx(過負荷)・429(レート制限)・408(タイムアウト)とスキーマ検証落ち(生成のブレ)。それ以外の4xx(APIキー不正・モデル名不正・リクエスト不正)は投げ直しても同じ結果になり、待ち時間だけが倍になるため即座に返す

### 10.1 取り込み(スプレッドシート→アプリ。Issue #54)

スプレッドシートを復元可能なバックアップとして使うための、シート→アプリ方向の手動取り込み。機種変更・ブラウザデータ消失時の復元と、シートに手入力した過去データの移行に使う。

1. トリガー: 設定画面の「シートから取り込み(復元)」ボタンのみ(全タブの取り込みは自動では実行しない。Garmin由来の活動記録タブだけは別途、自動同期のたびに取り込む。10.2章参照)
2. 読み取り: クライアント(`runImport`)が `GET /api/import-sheets` を呼び、Workerが**全タブ**の全行を読み取ってレコード形式に逆変換して返す(読むタブの一覧は `worker/sheetsImport.ts` の `handleImportSheets` が正。10章のとおり本書はタブを列挙しない)。**タブ自体が無ければ空として扱う** — Garmin連携が書き込む活動記録タブは未連携なら存在せず、後付けのタブも初回同期前のシートには存在しないため、どちらも取り込み全体を失敗させない
   - 行の解析はトレラントに行う: 日付・日時はSheetsのロケール表示や手入力を考慮して複数表記(`yyyy年mm月dd日`・`yyyy/m/d`・`yyyy-m-d`、時刻省略可=JST 00:00扱い)を受け付け、数値は桁区切りカンマを許容する。解釈できない行はスキップして件数を返す(1行目は見出し行とみなしスキップ数に数えない)
   - 手入力行を想定し、体重の体脂肪率・メモ・記録日時、食事のPFC(省略時0)、水分・筋トレ・日記の記録日時(省略時はその日のJST 00:00)は省略可。食事の日時・区分・品名・カロリー、体重の日付・体重、水分の記録日時・摂取量、筋トレの日付・種目名・種目順・セット番号・重量・回数、日記の日付は必須(日記の気分・本文・飲酒は空を許容。飲酒列は「あり」のほかチェックボックス・手入力を想定した表記(TRUE・○・1)もtrueとして受け付け、それ以外は「記録なし」扱い。Issue #112)
   - マスタも同様に手入力行を想定する: 食事マスタは品目名・カロリーが必須でPFC(省略時0)・出典は省略可、種目マスタは種目名のみ必須。登録日時は省略時=取り込み時刻とする(マスタには代わりに使える日付キーが無いため)。同名(前後空白無視)の2行目以降は重複としてスキップする(#96)
   - **ID列が空の行にはWorkerがIDを採番し(体重=日付、食事・水分・筋トレ=UUID、日記=日付、食事マスタ・種目マスタ=UUID、血圧・周囲径=日付、習慣マスタ=UUID、習慣記録=`${日付}_${習慣ID}`の合成キー)、その場でシートに書き戻す**。書き戻さないと以後の同期(ID列キーのupsert・行削除)が該当行を見つけられず重複行を生むため、書き戻しに失敗した場合は取り込み全体を失敗させる。活動記録タブはID列を持たない(日付が主キーで、アプリ→シート方向の同期が無いため採番・書き戻しも不要)
3. マージ(クライアント側): **追加のみ**
   - ローカルに同じキー(体重・日記=日付、食事・水分・筋トレ・マスタ=ID)の記録が既にあればスキップする(ローカル優先。シート側の編集でローカルを上書きしない)
   - マスタはIDが違っても同名(前後空白無視)の既存品目・種目をスキップする — 手入力行はID採番前にローカルと同名になりえ、種目マスタは同名を許さない(サジェストのキーが名前)ため(#96)
   - 削除トゥームストーンが保留中のキーもスキップする(未送信の削除が取り込みで復活するのを防ぐ)
   - 取り込んだ記録は`synced: true`で保存する(シート由来のため再送信不要。シート側に同じIDの行が存在するので、取り込み後にアプリで編集すれば通常のupsertで正しく反映される)
   - 例外として活動記録は「追加のみ・ローカル優先」にせず、常にシート側の値で上書きする(アプリ内に編集・削除が無く競合しないうえ、Garminのバックフィルによる過去日の訂正を反映するため。#81)
4. 制約
   - シートに無い情報は復元できない: 食事のAI推定値・写真参照、`apiToken`。これらは設定画面の「完全バックアップ(ファイル)」(9章、Issue #164)で別途退避する(食事マスタ・種目マスタは#96、週次・月次のAIコメントと設定は#164で同期・取り込みの対象になった)
   - シートの日時は分単位のため、復元されたタイムスタンプの秒以下は失われる

### 10.2 活動記録の自動取り込み(スプレッドシート→アプリ。Issue #133)

10.1章の手動取り込みとは別に、Garmin由来の**活動記録タブだけ**を自動同期のたびに取り込む。活動記録はGitHub Actionsのcron(毎日3:00 JST。CLAUDE.mdのGarmin連携参照)がシートへ書き込むため、手動取り込みボタンを押さなくてもアプリに反映されるようにする。

1. トリガー: 自動同期(10章のトリガー=起動時・アプリ復帰時・オンライン復帰時)のたび。既存のpush(`runSync`)に続けて活動記録の取り込み(`runActivityImport`)を実行する。スロットリング・再入抑止は自動同期のものをそのまま共有する。手動の「今すぐ同期」ボタンはpushのみ(活動記録の取り込みは含めない)、全タブの取り込みは引き続き「シートから取り込み」ボタンのみ
2. 読み取り: クライアント(`runActivityImport`)が `GET /api/import-activity` を呼ぶ。全タブを読む `GET /api/import-sheets` と違い、Workerは活動記録タブ1枚だけを読み取って返す軽量エンドポイント(自動同期のたびに叩くため)。行の解析は10.1章と同じ活動記録のパース(日付が主キー、ID列・書き戻しは無い)。タブ自体が無ければ空として扱う(Garmin未連携でも失敗しない)
3. マージ(クライアント側): 10.1章の活動記録と同じく「追加のみ・ローカル優先」にはせず、既存日付も常にシート側の値で上書きする(Garminのバックフィルによる過去日の訂正を反映するため。#81)。取り込んだ記録は`synced: true`で保存する
4. 失敗時: 取り込みはベストエフォートで、その成否は同期結果(push)には影響させない(`runActivityImport`はthrowせずエラーを返すだけ)。次回の自動同期で再度取り込みを試みる
