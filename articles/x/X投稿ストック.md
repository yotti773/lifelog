# X投稿ストック(単独ポスト・再放流)

記事の公開に紐づかない、**それ単体で完結するX投稿の在庫**。書き溜めておいて、上から順に消費する。

記事公開時の告知投稿は `X投稿テンプレート.md`(本文+自己リプの型)が正で、本ファイルはその**空白期間を埋める**ためのもの。方針の背景は `README.md` の「運用ルール」を参照。

## なぜ必要か

現状、X投稿は記事を出した日にしか発生していない。週次レポート(月曜)+ ストック記事(月1〜2本の木曜)なので、**週1〜2回しか投稿していない**ことになる。フォロワー実質0の段階でこの頻度だと、そもそも認知が積み上がらない。

一方で「投稿するために記事を書く」のは本末転倒(READMEの運用ルール「減量とアプリ開発が主、記事は従」に反する)。**すでに手元にある実データ・意思決定ログ・CLAUDE.md を、記事を書かずに1投稿ぶんに切り出す**のがこのファイルの役割。

## 単独ポストの型(告知ポストとの違い)

`X投稿テンプレート.md` のルールのうち、**単独ポストでは意図的に緩めるもの**が3つある。理由込みで残す。

| ルール | 告知ポスト | 単独ポスト | 理由 |
|---|---|---|---|
| 本文に外部リンクを貼らない | 必須 | **そもそもリンクが無い** | 単独ポストはリーチのペナルティが構造的に無い。ここが最大の利点で、実験的な文面を試す場としても向く |
| 画像を1枚付ける | 必須 | **流用が効くときだけ** | 1日1本のペースで全部に画像を作ると運用が破綻する。各投稿のメタ欄に流用可能な既存画像を書いてある |
| ~~アプリ名「からだログ」を毎回入れる~~ | 必須 | **必須(2026-08-08に撤回。緩めない)** | 下記「撤回したルール」を参照 |

緩めないもの(告知ポストと共通):

- **アプリ名「からだログ」と、それが何かを1行入れる**(下記「撤回したルール」)
- ハッシュタグは1〜2個
- 先頭1行は具体・数字・痛み・結果のどれか
- 付いた反応には全部返信する
- 読者層を混ぜない(技術ネタの自己リプに減量noteをぶら下げない、など)

### 撤回したルール: 「アプリ名は週1本でよい」(2026-08-08)

当初、B(技術ネタ)だけ**アプリ名の1行を省いてよい**ことにしていた。34本すべてに同じ定型句を入れると読み味が死ぬ、という理由だった。**これを撤回し、全カテゴリで必須に戻した。**

- 本人がB-01を見て「前提がないと何が何やらわからないポスト」と指摘した。実際そのとおりで、B-01は「誰が何を作っていて踏んだバグなのか」がどこにも無かった
- `X投稿テンプレート.md` には zenn03 の実例から得た逆の結論が既にあった —「技術詳細だけになり、初見の人が誰が何を作っている人なのか掴めないまま流れていく。**名前を出さずに『自作アプリ』とだけ書くのも不足**」。自分で書いたルールを、後から作った本ファイルで上書きしていた
- **「定型句がうるさい」への対処は、省略ではなく言い回しを変えること。** 14本それぞれで「体重と食事を記録する自作PWA『からだログ』」「自作の記録アプリ『からだログ』」「減量アプリ『からだログ』」のように文脈への差し込み方を変え、同じ文が並ばないようにした
- 自己リプの記事リンクでは代替できない。**自己リプは大半の人が開かない**うえ、リンクを出せるのはBの14本中3本(B-01→zenn02、B-05・B-07→zenn03)だけで、残り11本は対応する記事が無い

### 文字数の上限(必須の検証)

**X の上限は重み付き280 = 日本語で実質140字。** 日本語のかな・漢字・全角約物はすべて重み2、ASCII・ラテンは重み1で数える(twitter-text の weightedLength)。URLはt.co短縮のため実長に関わらず23文字。

**投稿文を書いたら、確定前に必ず実測する。**

```
node scripts/x/check_post_length.mjs          # ストック全件(超過があれば exit 1)
echo "本文" | node scripts/x/check_post_length.mjs -   # 1本だけ測る
```

初版は上限を検証しておらず、**34本中8本(A-03・A-05・A-09・B-01・B-02・B-03・B-08・B-14)が超過していた**(最大312)。アプリ名の1行を足す修正と削る修正が同時に必要になり、17本を書き直すことになった。**先に測っていれば避けられた手戻りなので、補充のたびにスクリプトを回すこと。**

## カテゴリ

- **A. 実データ系**(12本) — スプレッドシートの実データから作る「信じている数字が違う」型。想定読者は増減量サイクルを回す層+個人開発クラスタ。note06(実測TDEE)・需要検証2本目3本目と同じ鉱脈なので、**記事公開前に同じ数字をXで出しすぎない**よう、記事の公開日近辺では温存する
- **B. 開発の小ネタ**(14本) — 意思決定ログ・CLAUDE.md から拾う技術/判断の1ネタ。想定読者はエンジニア層。`X投稿テンプレート.md` の記入例で確認済みの「**gotchaより判断から入るほうが射程が広い**」に従い、gotcha系と判断系を混ぜてある
- **C. 既存記事の再放流**(8本) — 公開済みのnote/Zenn 5本+別プロジェクト1本を、**公開時とは別の切り口・別の画像**で再投稿する。C-08だけは固定ポスト候補

## 消費と補充のルール

- **1日1本まで。連投しない。** 在庫があると一気に出したくなるが、タイムラインを占有すると逆効果
- **カテゴリを日替わりでローテーションする**(A → B → C → A …)。読者層が違うので、同じカテゴリが3日続くと片方が飽きる
- **消費したらメタ欄の `使用日` を埋める。** 同じ文面を二度出さない。行は消さずに残す(何が伸びたかを後から見るため)
- **`使用日` はメタ欄に投稿当日に書く。PRは週次でまとめる**(2026-08-08決定、2026-08-09に手動投稿への切り替えに合わせて前提を修正)。1本消費するたびにPRを作ると9/18まで30回以上、1行を埋めるだけのPRを繰り返すことになり、記録としての価値に手数が見合わない。**月曜の週次レポート作業のついでに、その週に消費した5〜6本ぶんのコミットをまとめて作る。**(旧: 「予約済みのぶんは既にキューに入っていて記録の実益が薄い」としていたが、手動投稿に統一した以上この前提は成り立たない。当日に手元でメタ欄を更新し、コミットだけ週次にまとめる)
- **数字には消費期限がある。** カテゴリAの数値は 2026-08-05 時点の実データ(2026-05-18〜08-02の77日間)。週次レビュー由来の数字(必要ペース・着地予測)は毎週変わるので、**投稿前にアプリの週次レビュー画面で最新値に差し替える**。該当する投稿にはメタ欄に `要更新` と書いてある
- **補充の湧き口**: `docs/からだログ_意思決定ログ.md`(特に「対応不要としてクローズ」した判断は、やったことより強い)・`CLAUDE.md` の「注意点」「〜しないこと」系の記述・週次レビュー画面の実データ・Issueのクローズ理由

## 予約投稿の運用

**2026-08-09: 手動投稿に統一した(方針転換、以下の「公式予約×手動のハイブリッド」は廃止)。** きっかけはA-06(2026-08-09投稿分)。公式予約に乗せる条件が「本文にリンクが無く自己リプも不要」だったため、A・Bの大半は自己リプ・画像を付けずに本文だけで完結させていた。A-06に画像+自己リプ(内容に一番近い既存記事へのリンク+レーン導線)を足したところ本人が明確にクオリティ向上を実感し、**頻度(予約でまとめて流す)より質を優先する**運用に切り替えた。

新しい運用:

- **すべて手動投稿。** 投稿カレンダー(下記)の順に、その投稿の `使用日` が来た当日に初めて本文を仕上げる。仕上げる内容は2つ: (1) 自己リプ(内容に一番近い既存記事、またはレーン導線となる過去記事)・流用できる画像の有無を確認し、あれば足す、(2) フックの言い回し・数字の見せ方を当日の目で磨き直す
- **前もって30本まとめて仕上げない(2026-08-09決定)。** 画像選定・リンク先選定の判断を一度に積むと作業が重くなるため、使う日ごとに1本ずつ仕上げる。ストックの各エントリは「まだ仕上げる前の下書き」として残っている状態でよい
- **公式予約(無料・64件・スレッド不可)は使わない。** 貼り付け用一覧ファイル・生成スクリプトは役目を終えたため削除した(`X予約投稿_貼り付け用.md`・`scripts/x/generate_paste_list.mjs`、2026-08-09)
- **投稿する時刻の目安は据え置き。** B(技術ネタ)は平日8:00・土日9:00、A(実データ)は22:00、Cは`X投稿テンプレート.md`の投稿前チェックリストに沿う(下記の時間帯の理由は変わらないため)
- **反応への返信は引き続き手動。** ここは元々自動化されていなかったので変更なし
- **`使用日`はその日のうちに埋める。** 予約キューに事前投入する運用ではなくなったため、「週次でまとめて記録する」(下記「消費と補充のルール」)の前提が崩れている。当面は投稿の都度メタ欄を更新し、コミット・PRは引き続き週次(月曜の週次レポート作業のついで)でまとめてよい — 記録の即時性とPR頻度は別の話なので、後者の運用は変えない

毎日投稿を手作業で回すのは続かないため、予約投稿に乗せる。調べた結果、**公式の予約投稿(無料)で大半は賄えるが、スレッドだけは予約できない**ことが分かった。

| | X公式の予約投稿 | X API(GitHub Actions cron) |
|---|---|---|
| 費用 | **無料** | **従量課金**(2026年2月に無料枠が廃止)。投稿1件$0.015、**リンクを含む投稿は1件$0.20** |

**採用: 公式の予約投稿で回す(ハイブリッド)。**

- **カテゴリA・Bのうち24本を公式予約に流し込む。** 単独ポストは本文にリンクが無く自己リプも不要なので、公式予約の「単独ポストのみ」という制約に完全に噛み合う。64件の上限にも収まる
- **`要更新`・`要確認` の A-08・A-09 は予約から外して手動投稿にする**(下記「予約投稿でも自動化されないこと」)。数字の差し替え・裏取りが要るものを先に予約すると、当日に気づけない
- **カテゴリC(8本)も手動投稿。** 再放流は自己リプで記事URLを出す型なので、予約するとリンクが落ちる。週1本ペースなら手動で足りる
- **B-01・B-05・B-07 の自己リプは任意なので、予約に回すときは省く。** 本文だけで完結する文面にしてある

**内訳: 予約24本(A 10 + B 14)/ 手動10本(A-08・A-09 + C 8本)。**

**予約する時刻**は `X投稿テンプレート.md` の投稿前チェックリスト(平日 朝7〜9時/昼/夜21〜23時、技術記事は平日朝が伸びやすい)に沿って、**B(技術ネタ)は平日8:00・土日9:00、A(実データ)は22:00**で固定する。カテゴリごとに時間帯を分けているのは、読者層が違うため — Bはエンジニアの通勤・始業前、Aは減量/個人開発クラスタが動く夜に寄せる。

**X APIを採らなかった理由**: 月30本なら投稿ぶんは$0.45程度だが、**リンクを含む投稿が1件$0.20**と桁が違う。自己リプで記事URLを出す型と最も相性が悪い課金体系で、Cカテゴリを自動化すると月$2〜2.5(約350円)かかる。公式予約が無料でA・Bを丸ごと吸収できる以上、Cの8本を手動でやるほうが安い。**将来、投稿本数が増えてCの比率が上がったら再検討する**(既に `.github/workflows/garmin-sync.yml` でcron+Secretsの運用実績があるため、作ること自体の障壁は低い)。

### 予約投稿でも自動化されないこと

- **反応への返信は手動のまま。** `X投稿テンプレート.md` の「付いた反応には全部返信する。会話がいちばん評価される」は予約投稿でも変わらない。**投稿だけ自動で流れて会話がゼロだと、頻度を上げた意味が無くなる**ため、予約で浮いた時間は返信に充てる
- **`要更新`・`要確認` の4本(A-08・A-09・C-06・C-07)は予約に流さない。** 数字が変わる/裏取りが要るため、投稿直前に手で確認してから出す
