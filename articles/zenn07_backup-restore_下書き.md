ローカルファーストのPWAを個人開発しています。体重・食事・水分・筋トレ・日記を記録して、週次でAIにコーチングさせるアプリです。データはIndexedDB(Dexie)に持ち、Google スプレッドシートへ同期しています。

先日、**Cloudflare のworkers.devサブドメインを変えたくなりました**。個人ID由来の名前を、もう少し中立な名前にしたかっただけです。ダッシュボードで1箇所変えれば終わる、5分の作業のはずでした。

結果として、**バックアップ機構を作り直し、3回のコードレビューで20件を修正し、1週間分の作業になりました。**

そのあいだに「そう書いてあったのに、実際は違った」ことが4つ見つかりました。どれも自分で書いた仕様書とコードです。同じ構成でPWAを作っている人には、そのまま踏み抜きうる地雷だと思うので共有します。

## 3行まとめ

- **IndexedDBはオリジン単位。** 配信URLが変わると同じブラウザでもデータは引き継がれず、しかも変更後は旧オリジンを開けなくなるので、取り残したデータの救出手段も同時に消える
- **「ロジックは残置してあるので容易に戻せる」と仕様書に書いてあったバックアップは、16テーブル中3つしか対応していなかった。** 使われないコードは腐る
- **検証していないバックアップはバックアップではない。** 実際にリハーサルしたら、その場で新しいバグが1つ見つかった

## 発端: 5分で終わるはずだった

`wrangler.toml` にサブドメインの記述はありません。Cloudflare のworkers.devサブドメインは**アカウント単位の設定**で、ダッシュボードから変えるとその配下のWorkerのURLが一斉に変わります。リポジトリ側の変更はゼロ。

なので当初は「ダッシュボードで変えて、ドキュメントのURLを置換して終わり」と考えていました。実際、ドキュメント側の更新だけは数週間前に済ませてあり、Cloudflare側の操作だけが残っている状態でした。

作業に取りかかる直前に、ふと気づきます。

**このアプリ、データをIndexedDBに持っているのでは?**

## 罠1: IndexedDBはオリジン単位で、旧オリジンは開けなくなる

IndexedDB のストレージは**オリジン(スキーム + ホスト + ポート)ごとに分離**されています。これはPWAに限らずWeb Storage全般の基本ルールで、localStorage も Cache API も同じです。

つまり `https://lifelog.aaa.workers.dev` と `https://lifelog.bbb.workers.dev` は、**同じブラウザの同じユーザーであっても完全に別のデータ領域**です。ホスト名が1文字違えば別物です。

ここまでは、言われれば当たり前の話です。厄介なのは次でした。

**サブドメインを変えた瞬間、旧オリジンは到達不能になります。** 自分のWorkerはもう `https://lifelog.aaa.workers.dev` では配信されないので、このURLを開いてもアプリは出てきません。開けないということは、**そこに残っているIndexedDBのデータを取り出す手段も同時に消える**ということです。

ここには不快な非対称があります。**旧サブドメイン名は解放され、他のアカウントが取得しうる状態になります。** そこに誰かがページを置けば、そのページは旧オリジンと同一オリジンで動くので、**端末に residual として残っているIndexedDBを読めてしまいます**。

つまり移行後の旧オリジンは、**自分は開けないのにデータは残り続け、そのサブドメインを取得した第三者からは読める**という状態です。切り替えの前に、旧URLを開いていた端末のサイトデータを消しておくのが安全です(ブラウザの設定 → サイトごとのデータ削除)。切り替えた**後**では、自分の手では消せなくなります。

通常のデータ移行なら「新環境で不足に気づいたら、旧環境に戻って取り直す」ができます。この移行にはそれがありません。**やり直しが効かない一方通行**です。

:::message alert
独自ドメインで運用していれば、DNSを戻せば旧オリジンに戻れます。この一方通行性は「プラットフォームが払い出すサブドメインを、解放を伴う形で変更する」場合に固有の話です。逆に言えば、**独自ドメインを最初から当てておけば避けられた問題**でもあります。
:::

というわけで、移行の前にバックアップと復元経路を確認することにしました。ここからが本題です。

## 罠2: 「容易に戻せる」と書いてあったコードは腐っていた

このアプリには、以前JSONエクスポート機能がありました。UIリニューアルの際に画面からは消しましたが、そのときのIssueにこう書いてありました。

> UIは削除したがロジックは残置されている

要件定義書にも「完全バックアップが必要な場合はこちら」という位置づけで残っていました。なので「UIを戻すだけの簡単な作業」だと思っていました。

実物を見たら、こうなっていました。

```ts
// 復活させようとしたときの db/backup.ts(抜粋)
export interface BackupData {
  exportedAt: string;
  weightRecords: WeightRecord[];
  mealRecords: MealRecord[];
  settings: Settings;
}
```

**3テーブルです。** UIを消した時点ではそれで正しかったのですが、その後アプリはフェーズ2〜4と拡張され、水分・日記・筋トレ・種目マスタ・週次AIコメント・活動記録・月次AIコメント・血圧・周囲径・習慣マスタ・習慣記録……と**16テーブルまで増えていました**。

「残置してあるから容易に戻せる」という仕様書の記述は、**書いた時点では正しく、その後静かに嘘になっていた**わけです。UIから切り離されたコードは呼ばれないので、テストも通り続けるし、型エラーも出ません。腐っていることに気づく機会がどこにもありません。

しかも最悪なのは、この状態で「復元」を実行しても**エラーにならない**ことです。3テーブルだけ復元され、残り13テーブルは空のまま。成功したように見えます。

### 対処: 網羅をテストで縛る

作り直すにあたって、**同じ腐り方を二度としないための番人**をテストに置きました。

```ts
describe("バックアップ対象テーブル", () => {
  it("syncDeletions以外のすべてのテーブルを対象にしている", () => {
    // テーブルを足したのにバックアップに入れ忘れる事故を防ぐ。実際にフェーズ2以降の
    // テーブルが漏れたまま放置されていた(Issue #164)
    const all = db.tables.map((table) => table.name).sort();
    const covered = [...BACKUP_TABLES, "syncDeletions"].sort();
    expect(covered).toEqual(all);
  });
});
```

Dexie は `db.tables` でスキーマ上の全テーブルを列挙できます。これと `BACKUP_TABLES` を突き合わせれば、**テーブルを追加してバックアップに入れ忘れた瞬間にテストが落ちます**。

ポイントは「16個のテーブル名を書いた配列」を検証しているのではなく、**スキーマそのものを正として突き合わせている**ことです。前者だとテスト自体が腐ります。

`syncDeletions`(同期の削除トゥームストーン置き場)だけは意図的に除外しており、それも明示的に書いてあります。「なぜ除外されているか」がコードから読めないと、次に見た人が「漏れているのでは」と迷うためです。

## 罠3: 却下理由の前提が、いつのまにか崩れていた

JSONバックアップを直したあとで、素朴な疑問が出ました。

**「スプレッドシート同期とJSONバックアップ、バックアップ機構が2つあるのはどうなのか?」**

このアプリは全記録をスプレッドシートへ自動同期しており、シートからアプリへ戻す取り込み機能もあります。つまりシート同期は既に「自動で最新に保たれるバックアップ」として機能しています。一方JSONは手動なので、**放っておけば必ず古くなります**。二重に持つ意味があるのか。

調べると、当時のIssueには「AIコメントをシートのタブにする案」を却下した理由がこう書いてありました。

> `AdviceRecord` は生成時の `digest`(ネストした構造化データ)も再現・デバッグ用に保存しているため、1セルにJSON文字列を詰めることになり、「シートは人間が読める閲覧用の写し」という同期の利点を損なう

もっともらしい理由です。が、念のため確かめました。

```
$ grep -rn "\.digest" src/
(該当なし)
```

**`digest` は、アプリのどこからも読まれていませんでした。**

週次レビュー画面が表示している数値は、`getWeeklyDigest()` が毎回レコードから計算し直したものです。保存された `digest` は書き込まれるだけで、二度と参照されていませんでした。

つまり却下の理由になっていた「ネストした構造化データ」は、**そもそもシートに載せる必要がないデータ**でした。失って困るのは `advice`(判定・総評・良かった点・アクション)というテキスト4項目だけで、これは普通のシート1タブに素直に収まります。

この確認を経て、AIコメントと設定をシート同期の対象に加えました。結果、**JSONでしか戻せないのは食事のAI推定値・写真参照・APIトークンだけ**になり、二重管理の重複はほぼ解消しました。

:::message
**教訓**: 過去の自分が書いた「〜なので却下」は、根拠の部分だけ独立に検証できることがあります。結論ではなく**根拠**を確かめると、前提が崩れていることに気づけます。今回は `grep` 一発でした。
:::

## 罠4: リハーサルが、その場で新しいバグを見つけた

ここまでで保全の仕組みは整いました。が、**まだ一度も復元を試していません。**

そもそもこの作業の発端になったIssueには、こう書いてありました。

> バックアップは復元を検証して初めてバックアップとして成立するため、動くつもりで動かない状態が続いているかもしれない

なので、ドメインを変える前にリハーサルをやりました。やり方はこうです。

**同一オリジンのプライベートウィンドウで開く。**

これがきれいにハマりました。プライベートウィンドウは IndexedDB が空で、かつオリジンは本番と同じです。つまり**「移行直後の端末」とまったく同じ状態を、URLを変える前に、本番データを危険に晒さずに再現できます**。

手順は「APIトークンを入力 → シートから取り込み」。実際にやってみて、想定どおりデータは戻りました。そして**想定していなかったバグが1つ出ました**。

### トークンだけ入れた端末が、永久に同期待ちになる

APIトークンを入力した直後、**未同期件数のバッジが「1」のまま消えなくなりました。**

原因はこうです。このアプリは設定もシートへ同期していますが、**`apiToken` だけは対象外**にしています。取り込みAPIの呼び出しに `Authorization: Bearer` としてこの値が要るため、入力済みでなければ取り込みが始まらず、**シートからは原理的に復元できない**からです(認証情報をシートに置きたくない、という理由とも一致します)。

一方で、設定行そのものには「未同期フラグ」を持たせて差分同期していました。

```ts
// 修正前: 行が未同期かどうかで判定していた
if (
  unsyncedWeightRecords.length === 0 &&
  // ...
  unsyncedSettings === null &&
  // ...
) {
  return { status: "skipped-nothing-to-sync" };
}
```

トークンだけを入れた端末は、**「設定行は未同期。でも送信できる項目は0件」**という状態になります。行を見れば未同期なのでバッジは1を表示し、同期は走るが送るものが無く、いつまで経ってもフラグが下りません。空のペイロードを送り続けます。

```ts
// 修正後: 「送信できる項目があるか」で判定する
// 設定は「行が未同期か」ではなく「送信できる項目があるか」で判定する。
// APIトークンだけ入れた端末(移行直後にまさにこの状態)は送信対象が0件で、
// 行の未同期フラグだけを見ると永久に同期待ちのまま残ってしまう
const settingsEntries = unsyncedSettings ? toSettingsEntries(unsyncedSettings) : [];

if (
  // ...
  settingsEntries.length === 0 &&
  // ...
```

データが壊れるバグではありません。が、**移行後の端末が必ず通る状態**で、しかも「バッジが消えない」という気持ち悪さが永続します。そして重要なのは、**リハーサルをしなければ本番で踏んでいた**ということです。

「バックアップは復元を検証して初めて成立する」という前提が、そのまま1件の不具合として現れました。

## 罠5(おまけ): 既定値を保存してはいけない

リハーサル前のコードレビューで見つかった、これが一番危なかったものです。設定の読み書きがこうなっていました。

```ts
// 修正前(概念図)
export async function getSettings(): Promise<Settings> {
  const stored = await db.settings.get("default");
  return { ...DEFAULT_SETTINGS, ...stored };  // 既定値を被せて返す
}

export async function updateSettings(patch) {
  const current = await getSettings();          // ← 既定値込みのオブジェクト
  await db.settings.put({ ...current, ...patch }); // ← それをそのまま保存
}
```

読み取り時に既定値を被せるのは自然です。問題は、**そのマージ結果を保存してしまっている**ことでした。

新規端末で最初にやる操作は「APIトークンの入力」です。その瞬間 `updateSettings({ apiToken })` が走り、**既定値(目標体重64kg、目標カロリー1900kcal など)が「ユーザーが明示的に設定した値」としてDBに実体化します**。すると、

1. 次の自動同期で、**その既定値がシート上の実値を上書きする**。旧端末は同期済みなので再送信せず、実値はシートから恒久的に失われる
2. 「シートから取り込み」も既定値を「設定済み」とみなすため、**目標体重・目標日・目標カロリーという最重要の3項目を復元しない**

そして 2 は、取り込みにAPIトークン入力が必須である以上、**新規端末で必ず通る経路**でした。まさに今回の移行でやろうとしていたことです。

対処は「既定値は読み取り時にだけ被せ、保存行には明示的に設定された項目だけを持たせる」。型でそれを表現しました。

```ts
/**
 * **`Partial` なのは意図的**: 保存行には明示的に設定された項目だけを持たせ、既定値は
 * `getSettings()` が読み取り時に被せる。既定値を保存してしまうと「未設定」と区別できなくなり、
 * 新規端末の初回同期・取り込みが既定値を実値として扱う事故になる
 */
export type SettingsRow = Partial<Settings> & { id: "default"; synced?: boolean };
```

**「未設定」と「既定値のまま」を区別できることが、同期と取り込みの正しさの前提になっていた**、というのが構造的な学びでした。マージした値を保存するのは一見無害ですが、その瞬間に情報が1つ失われています。

## 罠6: 復元の「順序」

最後に、手順そのものの落とし穴です。移行先の端末には2つの復元経路があります。

- **シートから取り込み** — 追加のみ・ローカル優先でマージする
- **JSONから復元** — 全テーブルを削除してから書き戻す(完全な置き換え)

両方やれば万全な気がします。が、**「取り込み → JSON復元」の順は禁止**です。復元は全削除を伴うため、**先に取り込んだ内容は捨てられます**。

正しくは、**JSON復元だけを行えば完結します**。JSONはシートの内容を完全に包含し、さらにシートに無い食事のAI推定値・写真参照・APIトークンまで含むためです。APIトークンも戻るので再入力すら要りません。

自分でも一度この順序を取り違えて説明していました。「両方やっておけば安全」という直感が、**全削除を伴う操作の前では逆に働く**わけです。

## まとめ

サブドメインを1つ変えたいだけの作業でしたが、結果的にこの4つが見つかりました。

| | 書いてあったこと | 実際 |
|---|---|---|
| バックアップ機構 | ロジックは残置しており容易に戻せる | 16テーブル中3つしか対応していなかった |
| シートタブ案の却下理由 | `digest` がネストした構造化データだから | `digest` はどこからも読まれていなかった |
| 設定の保存 | (意識されていなかった) | 既定値が実値を上書きする経路があった |
| 未同期の判定 | (意識されていなかった) | 移行直後の端末が永久に同期待ちになる |

**共通しているのは、どれも「実際に動かすまで誰も嘘だと気づけなかった」ことです。** 型チェックもテストも通っていました。UIから切り離されたコードは腐り、却下理由の前提は静かに崩れ、既定値のマージは情報を1つ落としていました。

ローカルファーストは「サーバーが無いので気楽」という側面がある一方、**データの置き場がユーザーの端末しか無い**という重さがあります。その避難経路を一度も試したことがない状態は、避難経路が無いのとあまり変わりません。

そして今回いちばん効いたテクニックは、**同一オリジンのプライベートウィンドウでリハーサルする**ことでした。ドメインを変える前に、移行直後とまったく同じ状態を、失敗しても何も壊れない形で再現できます。同じ構成のPWAを移行する予定がある方は、ぜひ本番の前に一度試してみてください。
